# 데이터 수집 방식

각 플랫폼에서 사람들이 올린 불편·문제를 **어떤 방법으로 가져와 화면의 "문제"로 만들지** 정한다.
PRD F00(문제 데이터 생성 파이프라인)의 실행 설계이며, PRD 9절 TBD 중
"자동/수동 수집 범위"와 "하나의 문제로 묶는 최소 근거 기준"에 답하는 것이 목적이다.

| 문서 | 다루는 것 |
| :-- | :-- |
| [DATA_SOURCES.md](./DATA_SOURCES.md) | **어디서** 가져올 것인가 (플랫폼 목록, API/크롤링 구분, 법적 준수) |
| **이 문서** | **어떻게 · 언제** 가져와 문제로 만들 것인가 (시점, 쿼리, 판별, 묶기, 저장) |

---

## 1. 수집 시점 — 두 가지 모드

수집이 일어나는 순간은 두 가지이고, **둘은 목적도 제약도 다르다.**

| | **A. 정기 배치** | **B. 실시간 탐색** |
| :-- | :-- | :-- |
| 언제 | **주 1회** | 사용자가 플랫폼을 고르고 탐색을 요청할 때 |
| 목적 | **새로운 문제 발굴** | **지금 이 플랫폼에 어떤 얘기가 있는지 확인** |
| 기다리는 사람 | 없음 | **있음 (사용자가 화면에서 대기)** |
| 소스 | 전체 (크롤링 포함) | **API 소스만** |
| 파이프라인 | 6단계 전부 | 축약 (묶기·게시 생략) |
| 게시 기준 | 적용 ([6절](#6-문제로-묶는-기준)) | **미적용 → 다르게 표시해야 함** |
| 결과물 | 서비스의 정식 문제 목록 | 그 자리에서 보여주는 탐색 결과 |

이 구분이 흐려지면 **검증되지 않은 실시간 결과가 검증된 문제처럼 보이는 문제**가 생긴다.
PRD F03·F04가 "시장성·성공 가능성이 검증됐다고 표현하지 않는다"고 못박은 것과 같은 이유다.

### 1-1. A. 정기 배치 (주 1회)

- 전체 파이프라인 6단계를 모두 수행한다.
- 크롤링을 포함한 **모든 소스**를 쓴다. 사람이 기다리지 않으므로 요청 간 지연을 충분히 둘 수 있다.
- [6절 게시 기준](#6-문제로-묶는-기준)을 통과한 것만 정식 문제로 노출한다.
- 기준 미달 후보는 버리지 않고 쌓아둔다. **다음 주 배치에서 사례가 더 모이면 자동 승격된다.**

> 주 1회는 문제 발굴에 충분하다. 문제는 하루 만에 생겼다 사라지지 않는다.
> 오히려 주 단위로 모아야 "같은 불편이 여러 곳에서 반복되는가"를 판단할 표본이 쌓인다.

### 1-2. B. 실시간 탐색 (사용자 요청)

사용자가 **플랫폼을 선택하고** 탐색을 요청하면 그 자리에서 수집한다.

**할 수 있는 소스 / 없는 소스**

| 소스 | 실시간 | 이유 |
| :-- | :--: | :-- |
| 네이버 검색 API | ✅ | 응답이 빠르고 쿼터가 넉넉하다 |
| 카카오 다음 검색 API | ✅ | 위와 동일 |
| App Store 리뷰 RSS | ✅ | 단순 피드라 빠르다 |
| YouTube 댓글 | △ | `search.list`가 100 units라 비싸다. 선택 시에만 |
| 공공데이터 | △ | 페이지네이션이 느리다. 배치가 적합 |
| **Threads** | ❌ | **7일 500쿼리.** 사용자 트래픽에 열면 하루 만에 소진된다 |
| **커뮤니티 크롤링** | ❌ | **요청 간 2초 지연 규칙**을 지키면 사용자 대기 시간 안에 끝나지 않는다 |

> 크롤링을 실시간에 쓰지 않는 것은 성능 문제만이 아니다.
> 사용자 트래픽만큼 상대 서버에 요청이 가면 [7절](#7-하지-않을-것)의 "부담을 주지 않는다"를 지킬 수 없다.
> **크롤링은 배치 전용이다.**

**축약 파이프라인**

```text
[1 수집]  선택한 플랫폼에 쿼리 → 상한 100건
   ↓
[2 정제]  개인정보 제거 + 요약        (원문 폐기 정책은 배치와 동일)
   ↓
[3 판별]  불편 신호 필터              (규칙 기반이라 즉시)
   ↓
[표시]    묶기·게시 기준 없이 그대로 보여준다
   ↓
[적재]    같은 결과를 코퍼스에도 쌓는다 → 다음 배치에서 정식 문제로 승격 가능
```

마지막 **적재 단계가 중요하다.** 사용자의 탐색이 곧 수집이 되므로,
사람들이 많이 찾는 주제일수록 코퍼스가 빨리 쌓인다.

**응답 시간 목표**

| 구간 | 목표 |
| :-- | :-- |
| 검색 API 호출 (플랫폼 3개 × 3페이지) | 1초 이내 |
| 정제·판별 (규칙 기반) | 즉시 |
| 요약 생성 (AI, 병렬) | 3~4초 |
| **합계** | **5초 내외** |

5초는 사용자가 기다리기에 긴 시간이다. **진행 상태를 보여주거나, 도착한 플랫폼부터 순차로 노출**하는 편이 낫다.

**쿼터 보호**

실시간은 사용자 수만큼 호출이 늘어난다. 그대로 두면 하루 쿼터가 오전에 소진된다.

| 장치 | 내용 |
| :-- | :-- |
| 코퍼스 우선 조회 | 이미 수집된 결과가 있으면 API를 부르지 않는다 |
| 결과 캐시 | 같은 (플랫폼, 정규화 쿼리)는 6시간 재사용 |
| 사용자당 제한 | 분당 탐색 횟수 상한 |
| 플랫폼 선택 상한 | 한 번에 3개까지 |

**쿼터 상한 계산**: 탐색 1회 = 선택 플랫폼당 3 calls → 3개 선택 시 9 calls.
네이버 25,000 + 카카오 30,000이면 **하루 약 3,000회 탐색**이 상한이다.
사용자가 늘면 여기가 먼저 막히므로, 캐시 적중률이 곧 서비스 수용량이 된다.

**결과 표시 원칙**

실시간 결과는 [6절 게시 기준](#6-문제로-묶는-기준)을 통과하지 않았다. 따라서:

- **정식 문제와 같은 화면·같은 형식으로 섞어 보여주지 않는다.**
- "방금 OO에서 찾은 글" 성격임을 드러낸다. 관련 사례 수나 출처 분포를 정식 문제처럼 표시하지 않는다.
- 사례가 부족하면 부족하다고 표시한다. 숫자를 추정해 채우지 않는다.

> **PRD 반영 필요**: 현재 PRD F02(문제 탐색)에는 플랫폼 선택과 실시간 탐색이 없다.
> 이 모드를 넣으려면 F02에 입력(플랫폼 선택)과 출력(탐색 결과)이 추가되어야 하고,
> "정식 문제"와 "탐색 결과"를 화면에서 어떻게 구분할지도 F02·F03에 명시되어야 한다.

## 2. 전체 파이프라인

정기 배치 기준이다. 실시간 탐색은 [1-2절](#1-2-b-실시간-탐색-사용자-요청)의 축약 버전을 쓴다.

```text
[1 수집]      플랫폼별로 원문을 끌어온다
   ↓
[2 정제]      형식을 통일하고 개인정보를 제거한다
   ↓
[3 판별]      "이건 불편을 말하는 글인가"를 거른다
   ↓
[4 묶기]      같은 불편을 말하는 글들을 하나의 문제 후보로 모은다
   ↓
[5 구성]      문제 제목·설명·근거·출처를 만든다  → Problem / EvidenceItem / Source
   ↓
[6 게시]      기준을 넘긴 후보만 서비스에 노출한다
```

**핵심 원칙 하나**: 3단계까지는 기계적 규칙으로 좁히고, **AI는 4단계 이후에만 쓴다.**
수집 전량을 AI에 넣으면 비용이 감당되지 않고, 근거 없는 요약이 섞여 들어올 위험이 커진다.

## 3. 단계별 정의

### 3-1. 수집 — 원문 끌어오기

플랫폼마다 방식이 다르므로 [4절](#4-플랫폼별-수집-방법)에서 개별로 정의한다.
공통으로 남기는 필드는 아래와 같다.

| 필드 | 설명 |
| :-- | :-- |
| `platform` | 커뮤니티 / 리뷰 / 뉴스 / 소셜 (화면의 `SourcePlatform`과 동일) |
| `sourceName` | 매체명 |
| `sourceUrl` | 원문 링크 |
| `postedAt` | 원문 작성일 |
| `collectedAt` | 우리가 수집한 시각 |
| `collectedBy` | `batch` / `realtime` — 어느 모드로 들어왔는지 |
| `license` | 발췌·링크 허용 여부 (`summary-only` / `excerpt-ok`) |
| `contentHash` | 원문 해시 (중복 판정용) |

### 3-2. 정제 — 개인정보 제거와 원문 폐기

**여기서 원문을 버린다.** 판례와 PRD F03 정책을 지키기 위한 가장 중요한 단계다.
**배치와 실시간 모두 예외 없이 적용한다.**

1. 작성자 식별 정보(닉네임, ID, 프로필 링크), 전화번호, 이메일, 계좌번호를 제거한다.
2. 본문을 요약해 `summary`를 만든다.
3. **원문 전문은 저장하지 않고 폐기한다.** 남기는 것은 `contentHash`와 `sourceUrl`뿐이다.
4. `license`가 `excerpt-ok`인 경우에만 25자 이내 `excerpt`를 함께 남긴다.

> 원문을 데이터베이스에 쌓아두면 그 자체가 복제물이 된다.
> 해시만 남기면 중복 판정은 가능하면서 복제물은 보유하지 않는다.

### 3-3. 판별 — 불편을 말하는 글만 남기기

수집물의 대부분은 문제와 무관하다. 여기서 크게 줄인다.

**통과 조건** (모두 만족)

- 본문 길이 30자 이상 (한 줄 반응 제외)
- [5절 불편 신호 표현](#5-불편-신호-사전)이 1개 이상 등장
- 광고·홍보 패턴에 해당하지 않음 (구매 링크, 할인 코드, "체험단", "협찬")
- 동일 `contentHash`가 이미 없음

**보류 조건** (버리지 않고 미분류로 둔다)

- 카테고리를 특정할 수 없음
- 불편 신호는 있으나 대상이 불분명함 ("그냥 다 짜증난다")

### 3-4. 묶기 — 같은 불편끼리 모으기

**배치 전용 단계다.** 실시간 탐색에서는 시간이 부족해 생략한다.

1. **1차 — 키워드 겹침**으로 후보군을 좁힌다 (계산이 싸다).
2. **2차 — 임베딩 유사도**로 같은 불편인지 판정한다.
3. 묶인 덩어리를 **문제 후보(problem candidate)** 로 만든다.

같은 문제로 묶는 기준은 [6절](#6-문제로-묶는-기준)에서 정한다.

### 3-5. 구성 — 화면 타입으로 변환

`frontend/src/lib/types.ts`의 타입에 그대로 대응시킨다.

| 화면 필드 | 무엇으로 채우나 | 성격 |
| :-- | :-- | :-- |
| `Problem.title` | 묶인 글들에서 AI가 뽑은 한 문장 | **AI 서술** |
| `Problem.oneLiner` | 위와 동일 | **AI 서술** |
| `Problem.description` | 묶인 글들의 공통점을 AI가 서술 | **AI 서술** |
| `Problem.context` | 언제·누구에게 나타나는지 AI가 서술 | **AI 서술** |
| `Problem.category` | 분류기 결과 | 파생 |
| `EvidenceItem.summary` | 3-2에서 만든 개별 글 요약 3~5건 | **실제 근거** |
| `EvidenceItem.excerpt` | `license: excerpt-ok`인 건만 | **실제 근거** |
| `EvidenceItem.postedAt` | 원문 작성일 | **실제 근거** |
| `Source.name` / `platform` / `url` | 수집 메타 | **실제 근거** |
| `Source.caseCount` | 그 출처에서 이 문제로 묶인 글 수 | 집계 |
| `Problem.caseCount` | 이 문제로 묶인 전체 글 수 | 집계 |
| `Problem.relatedProblemIds` | 임베딩이 가까운 다른 문제 2~3개 | 파생 |
| `Problem.updatedAt` | 마지막 갱신 시각 | 집계 |

> 화면이 근거 영역과 AI 서술 영역을 색으로 구분하는 이유가 여기 있다.
> **위 표의 "AI 서술"은 전부 우리가 만든 문장이고, "실제 근거"만 수집된 사실이다.**
> 이 구분이 파이프라인 단계에서부터 유지되어야 화면에서도 정직하게 표시된다.

### 3-6. 게시 — 기준 통과분만 노출

[6절 기준](#6-문제로-묶는-기준)을 넘긴 후보만 서비스에 올린다.
미달 후보는 버리지 않고 쌓아둔다. 사례가 더 모이면 자동으로 승격된다.

## 4. 플랫폼별 수집 방법

### 4-1. 네이버 / 카카오 검색 API — 쿼리 설계가 전부다

**배치·실시간 양쪽에서 쓰는 주력 소스다.**

검색 API는 **무엇을 검색하느냐**가 성패를 가른다. 단순히 "회의록"을 검색하면
정보성 글만 나온다. **도메인 키워드 × 불편 표현**으로 조합해야 불편 글이 걸린다.

```text
쿼리 = [도메인 키워드] + [불편 표현]

  "회의록"    × "번거롭"      → 회의록 번거롭
  "가계부"    × "매번"        → 가계부 매번
  "이사"      × "뭐부터"      → 이사 뭐부터
  "동물병원"  × "얼마 나와"   → 동물병원 얼마 나와
```

| 항목 | 배치 | 실시간 |
| :-- | :-- | :-- |
| 도메인 키워드 | 카테고리별 사전에서 전체 순회 | **사용자 입력어** |
| 불편 표현 | 사전 전체 조합 | 상위 3~5개만 조합 (시간 제약) |
| 대상 | 지식iN, 카페글, 블로그, 웹문서 | 동일 |
| 정렬 | 최신순 (`date`) — 같은 상위 글의 반복 수집을 막는다 | 동일 |
| 페이지 | 쿼리당 3페이지 | 쿼리당 1~3페이지 |

> **지식iN이 가장 중요하다.** 질문 형식 자체가 "이런 게 불편한데 방법 없나요"라
> 불편 신호 판별을 거의 통과한다. 여기부터 붙이는 것을 권한다.

### 4-2. YouTube — 영상이 아니라 댓글을 판다

**배치 위주. 실시간은 사용자가 명시적으로 선택했을 때만.**

쿼터 설계가 중요하다. `search.list`는 100 units인데 `commentThreads.list`는 1 unit이다.

```text
1) search.list 로 카테고리별 영상을 소수만 찾는다   (100 units × 20회 = 2,000)
2) 찾은 영상의 commentThreads.list 를 깊게 판다      (1 unit × 500회 = 500)
                                                     ─────────────────────
                                                     주간 배치 2,500 units
```

실시간에서 매 요청마다 `search.list`를 부르면 100 units씩 나간다.
**영상 목록은 배치에서 미리 캐시해 두고, 실시간에는 댓글만 읽는 것**이 현실적이다.

**영상 선정 기준**: 리뷰·후기·비교 영상. 사용 중 불편이 댓글에 직접 달린다.
튜토리얼 영상은 "감사합니다" 류가 많아 회수가 낮다.

### 4-3. App Store 리뷰 RSS — 별점 낮은 리뷰가 금맥

| 항목 | 설정 |
| :-- | :-- |
| 대상 | 카테고리별 상위 앱 + 경쟁 앱 |
| 우선순위 | **1~3점 리뷰** (불편이 직접 서술된다) |
| 제외 | 5점 단문 ("좋아요") |
| 모드 | 배치 + 실시간 모두 가능 (단순 피드) |

### 4-4. 공공데이터 — 이미 정제되어 있다

**배치 전용.** 페이지네이션이 느려 사용자를 기다리게 할 수 없다.

한국소비자원 상담사례, 국민권익위 민원 데이터는 **성격 자체가 불편**이라
3-3 판별 단계를 사실상 건너뛴다.

다만 형식이 정형이라 **문장이 딱딱하고 서로 비슷하다.** 그대로 쓰면 근거가
관공서 문서처럼 보인다. 커뮤니티 데이터와 섞어서 균형을 맞춘다.

### 4-5. Threads — 배치 전용, 그것도 교차 검증용

**7일에 500쿼리**뿐이다. **실시간에는 절대 열지 않는다.**

```text
쓰지 말 것: 사용자 실시간 탐색에 연결        (하루 만에 소진된다)
쓰지 말 것: 새 문제를 찾으려고 넓게 검색
쓸 것:      이미 잡은 문제 후보가 SNS에서도 언급되는지 확인
```

| 항목 | 설정 |
| :-- | :-- |
| 배분 | 카테고리 8개 × 키워드 8개 = 64쿼리 / 일 → 주 448쿼리 (500 이내) |
| 정렬 | `RECENT` |
| 용도 | 문제 후보의 **교차 검증**, 최신 언급 확인 |

> 권한 승인(`threads_keyword_search`)에 시간이 걸리므로 **신청을 먼저 넣어 둔다.**

### 4-6. 커뮤니티 크롤링 — 배치 전용

사이트 전체를 긁지 않는다. **불편이 몰리는 게시판만 지정**한다.

| 사이트 | 대상 게시판 |
| :-- | :-- |
| 네이트판 | 고민 관련 게시판 |
| 뽐뿌 | 자유게시판 (구매·서비스 불만) |
| 클리앙 | 질문/팁 게시판 |
| OKKY | 질문 게시판 |
| 디스콰이엇 | 메이커 회고·고민 글 |
| 긱뉴스 | RSS + 댓글 |

**수집 규칙** (DATA_SOURCES.md 5절 준수 사항의 구현)

```text
- robots.txt를 매 실행 전에 읽고 Disallow 경로는 건너뛴다
- User-Agent: EurekaBot/0.1 (+연락처 URL)  — 정체를 밝힌다
- 요청 간 2초 이상 지연, 동시 요청 1
- 4xx/5xx가 연속 3회면 그 사이트 수집을 중단한다 (우회 금지)
- 신규 글만 수집한다 (과거 전체 아카이빙 금지)
- 사용자 요청에 연동하지 않는다 — 주 1회 배치에서만 동작한다
```

## 5. 불편 신호 사전

3-3 판별 단계에서 쓰는 한국어 표현 목록이다.
**4-1의 검색 쿼리 조합에도 그대로 재사용한다.**

| 유형 | 표현 |
| :-- | :-- |
| 직접 불만 | 불편, 짜증, 답답, 번거롭, 귀찮, 스트레스 |
| 반복 노동 | 매번, 일일이, 계속, 또, 노가다, 손으로 |
| 해결책 탐색 | 방법 없나요, 어떻게 하나요, 다들 어떻게, 뭐부터, 추천 좀 |
| 실패·포기 | 안 되네요, 왜 안, 포기, 실패, 그만뒀 |
| 결핍 | 있었으면, 아쉽, 없어서, 개선됐으면 |
| 시간 낭비 | 오래 걸려, 하루 종일, 시간 낭비, 한참 |

실시간 탐색에서는 시간이 부족하므로 **유형별로 정밀도가 높은 1~2개만** 골라 쓴다.

> 이 사전은 **고정이 아니다.** 실제 수집 결과를 보고 정밀도가 낮은 표현은 빼고,
> 놓치는 표현은 추가한다. 버전을 남겨 언제 무엇을 바꿨는지 추적한다.

**주의**: 표현이 있다고 곧 불편은 아니다 (예: "짜증나게 재밌다").
1차 필터로만 쓰고, 최종 판정은 묶기 단계에서 맥락과 함께 본다.

## 6. 문제로 묶는 기준

PRD 9절 TBD "하나의 문제로 묶는 최소 근거 기준"에 대한 제안이다.
**정기 배치에만 적용된다.** 실시간 탐색 결과는 이 기준을 통과하지 않은 상태로 표시된다.

| 단계 | 조건 | 처리 |
| :-- | :-- | :-- |
| **후보 생성** | 유사한 글 5건 이상 | 후보로 등록, 미노출 |
| **게시 가능** | 관련 사례 **20건 이상** + 서로 다른 출처 **3곳 이상** + 근거로 쓸 요약 **3건 이상** | 정식 문제로 노출 |
| **보류** | 사례는 많으나 출처가 1곳 | 노출하지 않음 |

**출처 3곳 조건이 핵심이다.** 한 커뮤니티에서만 100건이 나온 것은
"그 커뮤니티의 화제"이지 "세상의 문제"가 아닐 수 있다.
서로 다른 플랫폼에서 반복되어야 실재하는 문제로 본다.

화면의 `Problem.evidence`는 3~5건만 노출하므로, 묶인 것 중
**서로 다른 출처에서 하나씩** 고르는 것을 기본으로 한다. 한 출처 글만 5개 보여주면
근거가 편중되어 보인다.

## 9. 깨질 때 대비

| 상황 | 대응 |
| :-- | :-- |
| 크롤러가 마크업 변경으로 실패 | 해당 소스만 중단, 나머지는 계속. 실패를 알림으로 남긴다 |
| API 정책·가격 변경 | DATA_SOURCES.md를 갱신하고 대체 소스로 전환 |
| **실시간 중 쿼터 소진** | 코퍼스에 이미 있는 결과만 보여주고, 실시간 수집이 불가함을 표시한다. 숫자를 채워 넣지 않는다 |
| **실시간 응답 지연** | 도착한 플랫폼부터 순차 노출. 전체를 기다리게 하지 않는다 |
| 특정 출처가 과대 대표됨 | 출처별 상한을 두어 한 곳이 `caseCount`의 절반을 넘지 않게 한다 |
| 요약 품질 저하 | 사람이 검수하는 샘플링 큐를 둔다 (초기에는 전수 검수) |

> **초기에는 사람이 검수한다.** 자동 파이프라인이 만든 문제를 그대로 노출하면
> 근거와 서술이 어긋난 문제가 섞인다. MVP 단계에서는 게시 직전에 사람이 본다.
> 다만 **실시간 탐색 결과는 검수를 거칠 수 없다.** 이것이 실시간 결과를
> 정식 문제와 구분해 표시해야 하는 또 하나의 이유다.

## 10. 구현 순서

| 순서 | 내용 | 산출물 |
| :-- | :-- | :-- |
| 1 | 네이버 검색 API 수집기 + 정제 | raw 아이템이 쌓인다 |
| 2 | 불편 신호 판별 + 중복 제거 | 후보 글이 걸러진다 |
| 3 | 묶기 + 문제 후보 생성 | 문제 후보가 생긴다 |
| 4 | 화면 타입으로 변환 + 사람 검수 | `src/data/*` 시드를 실제 데이터로 교체 |
| 5 | **주 1회 배치 스케줄링** | 정기 수집이 돌기 시작한다 |
| 6 | **실시간 탐색 엔드포인트 + 캐시** | 사용자가 플랫폼을 골라 탐색할 수 있다 |
| 7 | 카카오·YouTube·공공데이터 추가 | 출처 3곳 조건을 만족시킨다 |
| 8 | 커뮤니티 크롤링 추가 (배치에만) | 생산성/업무 카테고리를 채운다 |

**4단계까지 오면 프로토타입의 가짜 데이터를 진짜로 바꿀 수 있다.**
현재 프론트엔드는 `frontend/src/lib/data.ts` 한 곳만 교체하면 되도록 되어 있다.

**실시간(6단계)은 1~4가 끝난 뒤에 붙인다.** 정제·판별 로직을 배치에서 먼저 검증해야
실시간에서 이상한 결과가 사용자에게 바로 노출되는 일을 막을 수 있다.
