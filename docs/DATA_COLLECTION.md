## 1. 수집 시점 — 타겟 요청과 정기 배치

**2026-09-13 사용자 변경 결정.** 나이대·성별·직업·장소 입력에 맞게 수집한다.
이전 “MVP는 배치뿐” 및 “플랫폼 선택 후 축약 수집” 설계는 현재 온보딩 경로를 설명하지 않는다.

| | 타겟 수집 요청 | 정기 배치 |
| :-- | :-- | :-- |
| 시작 | 온보딩 입력 후 문제 정의 탐색 | 운영자가 별도 실행하는 배치 경로 |
| 조건 | 입력된 나이대·성별·직업·장소 | 카테고리·도메인 사전 |
| 처리 | 수집 → 정제 → 판별 → 묶기 → 근거 → 문제정의·검수 | 기존 배치 함수 유지 |
| 표시 | 해당 실행의 자료 및 검수 상태 | 승인되어 저장된 공개 문제 풀 |
| 게시 | 자동 공개하지 않음. 기준·AI 검수·사람 승인 필요 | 동일한 공개 게시 요건 적용 |

### 1-1. 입력 조건과 실제 근거의 구분

- 네 입력 항목 중 최소 두 항목을 채운다. 직업·장소는 각각 최대 다섯 키워드다.
- 입력값을 검색어에 반영한다. 여러 키워드의 조합 방식·전체 카테고리 분배·API 호출 상한은 구현 정책이며 사용자 확정 값으로 기록하지 않는다.
- 검색 응답의 제목·스니펫에서 입력한 필드들의 문구를 대조한 뒤 판별 후보로 선정한다. 직업·장소는 각각 입력 키워드 중 하나 이상, 나이대·성별은 입력했을 때 조건에 포함한다. 미확인 자료도 원문 저장소에 보존한다.
- 입력어가 함께 등장해도 글쓴이의 연령·성별·직업·장소가 확인된 것으로 보정하지 않는다. 문구 대조는 일차 관련성 검사이며 문맥·대상의 의미 관계까지 입증하는 검증이 아니다.
- 수집 실행별 원자료·판정·후보·결과를 분리하여 이전 타겟이나 과거 파일럿 자료가 섞이지 않게 한다.
- 요청 재전송·새로고침으로 같은 수집을 중복 실행하지 않게 하고, 실패와 정상적인 빈 결과를 구별한다.

### 1-2. 운영과 비용

실제 구현된 검색 API 경로를 사용한다. 검색 API 스니펫 경계를 유지하며 원문 링크를 따라 본문을 수집하지 않는다.
대기 시간·동시 실행·쿼리 수·페이지 수·LLM 투입량에는 상한을 두고 실행 보고서에 남긴다.
주간 배치 시각, 사용자별 이용량, 재수집 주기, 운영 저장소는 후속 운영 결정 사항이다.
현재 상한과 실행법은 [타겟 수집 실행 안내](TARGET_COLLECTION_RUNBOOK.md)를 따른다.

## 2. 전체 파이프라인

타겟 수집도 근거·문제정의 생성까지 같은 처리 단계를 거친다. 공개 게시 여부는 실행 완료 여부와 별도로 판단한다.

```text
[1 수집]      플랫폼별로 원문을 끌어온다
   ↓
[2 정제]      형식을 통일하고 개인정보를 제거한다
   ↓
[3 판별]      "이건 불편을 말하는 글인가"를 거른다
   ↓
[4 묶기]      같은 불편을 말하는 글들을 하나의 문제 후보로 모은다
   ↓
[5 구성]      문제 제목·설명·근거·출처를 만든다  → Problem / EvidenceItem / Source
   ↓
[6 게시]      기준을 넘긴 후보만 서비스에 노출한다
```

**핵심 원칙 하나**: 규칙으로 먼저 좁힌 뒤 제한된 자료에 AI 불편 판별·문제정의 생성을 적용한다.
수집 전량을 AI에 넣으면 비용이 감당되지 않고, 근거 없는 요약이 섞여 들어올 위험이 커진다.

## 3. 단계별 정의

### 3-1. 수집 — 원문 끌어오기

플랫폼마다 방식이 다르므로 [4절](#4-플랫폼별-수집-방법)에서 개별로 정의한다.
공통으로 남기는 필드는 아래와 같다.

| 필드 | 설명 |
| :-- | :-- |
| `platform` | 커뮤니티 / 리뷰 / 뉴스 / 소셜 (화면의 `SourcePlatform`과 동일) |
| `sourceName` | 매체명 |
| `sourceUrl` | 원문 링크 |
| `postedAt` | 원문 작성일 |
| `collectedAt` | 우리가 수집한 시각 |
| `collectedBy` | `batch` / `realtime` — 어느 모드로 들어왔는지 |
| `license` | 발췌·링크 허용 여부 (`summary-only` / `excerpt-ok`) |
| `contentHash` | 원문 해시 (중복 판정용) |

### 3-2. 정제 — 개인정보 제거와 원문 폐기

**여기서 원문을 버린다.** 판례와 PRD F03 정책을 지키기 위한 가장 중요한 단계다.
**배치와 실시간 모두 예외 없이 적용한다.**

1. 작성자 식별 정보(닉네임, ID, 프로필 링크), 전화번호, 이메일, 계좌번호를 제거한다.
2. 본문을 요약해 `summary`를 만든다.
3. **원문 전문은 저장하지 않고 폐기한다.** 남기는 것은 `contentHash`와 `sourceUrl`뿐이다.
4. `license`가 `excerpt-ok`인 경우에만 25자 이내 `excerpt`를 함께 남긴다.

> 원문을 데이터베이스에 쌓아두면 그 자체가 복제물이 된다.
> 해시만 남기면 중복 판정은 가능하면서 복제물은 보유하지 않는다.

### 3-3. 판별 — 불편을 말하는 글만 남기기

수집물의 대부분은 문제와 무관하다. 여기서 크게 줄인다.

**통과 조건** (모두 만족)

- 본문 길이 30자 이상 (한 줄 반응 제외)
- [5절 불편 신호 표현](#5-불편-신호-사전)이 1개 이상 등장
- 광고·홍보 패턴에 해당하지 않음 (구매 링크, 할인 코드, "체험단", "협찬")
- 동일 `contentHash`가 이미 없음

**보류 조건** (버리지 않고 미분류로 둔다)

- 카테고리를 특정할 수 없음
- 불편 신호는 있으나 대상이 불분명함 ("그냥 다 짜증난다")

### 3-4. 묶기 — 같은 불편끼리 모으기

**배치 전용 단계다.** 실시간 탐색에서는 시간이 부족해 생략한다.

1. **1차 — 키워드 겹침**으로 후보군을 좁힌다 (계산이 싸다).
2. **2차 — 임베딩 유사도**로 같은 불편인지 판정한다.
3. 묶인 덩어리를 **문제 후보(problem candidate)** 로 만든다.

같은 문제로 묶는 기준은 [6절](#6-문제로-묶는-기준)에서 정한다.

## 4. 플랫폼별 수집 방법

### 4-1. 네이버 / 카카오 검색 API — 쿼리 설계가 전부다

**배치·실시간 양쪽에서 쓰는 주력 소스다.**

검색 API는 **무엇을 검색하느냐**가 성패를 가른다. 단순히 "회의록"을 검색하면
정보성 글만 나온다. **도메인 키워드 × 불편 표현**으로 조합해야 불편 글이 걸린다.

```text
쿼리 = [도메인 키워드] + [불편 표현]

  "회의록"    × "번거롭"      → 회의록 번거롭
  "가계부"    × "매번"        → 가계부 매번
  "이사"      × "뭐부터"      → 이사 뭐부터
  "동물병원"  × "얼마 나와"   → 동물병원 얼마 나와
```

| 항목 | 배치 | 실시간 |
| :-- | :-- | :-- |
| 도메인 키워드 | 카테고리별 사전에서 전체 순회 | **사용자 입력어** |
| 불편 표현 | 사전 전체 조합 | 상위 3~5개만 조합 (시간 제약) |
| 대상 | 지식iN, 카페글, 블로그, 웹문서 | 동일 |
| 정렬 | 최신순 (`date`) — 같은 상위 글의 반복 수집을 막는다 | 동일 |
| 페이지 | 쿼리당 3페이지 | 쿼리당 1~3페이지 |

> **지식iN이 가장 중요하다.** 질문 형식 자체가 "이런 게 불편한데 방법 없나요"라
> 불편 신호 판별을 거의 통과한다. 여기부터 붙이는 것을 권한다.

### 4-2. YouTube — 영상이 아니라 댓글을 판다

**배치 위주. 실시간은 사용자가 명시적으로 선택했을 때만.**

쿼터 설계가 중요하다. `search.list`는 100 units인데 `commentThreads.list`는 1 unit이다.

```text
1) search.list 로 카테고리별 영상을 소수만 찾는다   (100 units × 20회 = 2,000)
2) 찾은 영상의 commentThreads.list 를 깊게 판다      (1 unit × 500회 = 500)
                                                     ─────────────────────
                                                     주간 배치 2,500 units
```

실시간에서 매 요청마다 `search.list`를 부르면 100 units씩 나간다.
**영상 목록은 배치에서 미리 캐시해 두고, 실시간에는 댓글만 읽는 것**이 현실적이다.

**영상 선정 기준**: 리뷰·후기·비교 영상. 사용 중 불편이 댓글에 직접 달린다.
튜토리얼 영상은 "감사합니다" 류가 많아 회수가 낮다.

### 4-3. App Store 리뷰 RSS — 별점 낮은 리뷰가 금맥

| 항목 | 설정 |
| :-- | :-- |
| 대상 | 카테고리별 상위 앱 + 경쟁 앱 |
| 우선순위 | **1~3점 리뷰** (불편이 직접 서술된다) |
| 제외 | 5점 단문 ("좋아요") |
| 모드 | 배치 + 실시간 모두 가능 (단순 피드) |

### 4-4. 공공데이터 — 이미 정제되어 있다

**배치 전용.** 페이지네이션이 느려 사용자를 기다리게 할 수 없다.

한국소비자원 상담사례, 국민권익위 민원 데이터는 **성격 자체가 불편**이라
3-3 판별 단계를 사실상 건너뛴다.

다만 형식이 정형이라 **문장이 딱딱하고 서로 비슷하다.** 그대로 쓰면 근거가
관공서 문서처럼 보인다. 커뮤니티 데이터와 섞어서 균형을 맞춘다.

### 4-5. Threads — 배치 전용, 그것도 교차 검증용

**7일에 500쿼리**뿐이다. **실시간에는 절대 열지 않는다.**

```text
쓰지 말 것: 사용자 실시간 탐색에 연결        (하루 만에 소진된다)
쓰지 말 것: 새 문제를 찾으려고 넓게 검색
쓸 것:      이미 잡은 문제 후보가 SNS에서도 언급되는지 확인
```

| 항목 | 설정 |
| :-- | :-- |
| 배분 | 카테고리 8개 × 키워드 8개 = 64쿼리 / 일 → 주 448쿼리 (500 이내) |
| 정렬 | `RECENT` |
| 용도 | 문제 후보의 **교차 검증**, 최신 언급 확인 |

> 권한 승인(`threads_keyword_search`)에 시간이 걸리므로 **신청을 먼저 넣어 둔다.**

### 4-6. 커뮤니티 크롤링 — 배치 전용

사이트 전체를 긁지 않는다. **불편이 몰리는 게시판만 지정**한다.

| 사이트 | 대상 게시판 |
| :-- | :-- |
| 네이트판 | 고민 관련 게시판 |
| 뽐뿌 | 자유게시판 (구매·서비스 불만) |
| 클리앙 | 질문/팁 게시판 |
| OKKY | 질문 게시판 |
| 디스콰이엇 | 메이커 회고·고민 글 |
| 긱뉴스 | RSS + 댓글 |

**수집 규칙** (DATA_SOURCES.md 5절 준수 사항의 구현)

```text
- robots.txt를 매 실행 전에 읽고 Disallow 경로는 건너뛴다
- User-Agent: EurekaBot/0.1 (+연락처 URL)  — 정체를 밝힌다
- 요청 간 2초 이상 지연, 동시 요청 1
- 4xx/5xx가 연속 3회면 그 사이트 수집을 중단한다 (우회 금지)
- 신규 글만 수집한다 (과거 전체 아카이빙 금지)
- 사용자 요청에 연동하지 않는다 — 주 1회 배치에서만 동작한다
```

## 5. 불편 신호 사전

3-3 판별 단계에서 쓰는 한국어 표현 목록이다.
**4-1의 검색 쿼리 조합에도 그대로 재사용한다.**

**2026-09-12 갱신 — 코드(`app/config/dictionaries.py`, `DICT_VERSION`)를 정본으로 동기화.** 한국어 ㅂ불규칙 활용형("번거로워"·"번거로우"·"아쉬워"·"아쉬웠")이 실제 글에서 어간만으로 안 걸려서 추가돼 있다.

| 유형 | 표현 |
| :-- | :-- |
| 직접 불만 | 불편, 짜증, 답답, 귀찮, 스트레스, 번거롭, 번거로워, 번거로우 |
| 반복 노동 | 매번, 일일이, 계속, 또, 노가다, 손으로 |
| 해결책 탐색 | 방법 없나요, 어떻게 하나요, 다들 어떻게, 뭐부터, 추천 좀 |
| 실패·포기 | 안 되네요, 안 돼서, 안 되더, 왜 안, 포기, 실패, 그만뒀 |
| 결핍 | 있었으면, 없어서, 개선됐으면, 아쉽, 아쉬워, 아쉬웠 |
| 시간 낭비 | 오래 걸려, 하루 종일, 시간 낭비, 한참 |

쿼리 조합에는 사전 전체가 아니라 **유형별로 정밀도가 높은 것만** 고른 `PAIN_SIGNALS_TIER1`(10개)을 쓴다. 나머지(`PAIN_SIGNALS_TIER2`, 26개)는 주차별로 로테이션해 사전 전체를 커버한다(쿼리 수를 늘리지 않기 위해).

> 이 사전은 **고정이 아니다.** 실제 수집 결과를 보고 정밀도가 낮은 표현은 빼고,
> 놓치는 표현은 추가한다. 버전을 남겨 언제 무엇을 바꿨는지 추적한다.

**주의**: 표현이 있다고 곧 불편은 아니다 (예: "짜증나게 재밌다").
1차 필터로만 쓰고, 최종 판정은 묶기 단계에서 맥락과 함께 본다.

### 5-1. 지불 신호 사전 (2026-09-12 신규, `PAYMENT_SIGNALS`) — ★ 위 사전과 완전히 분리

근거 상세 페이지 "① 돈이 걸린 문제인가"의 재료다. **`PAIN_SIGNALS`에 유형을 추가하는 방식으로 만들지 않았다** — 섞으면 4곳이 깨진다:

| # | 부작용 |
| --: | :-- |
| 1 | 통과율 상승 — "요금이 비싸다"가 3-3 판별을 통과하게 된다 |
| 2 | 랭킹 왜곡 — 신호 유형 다양성 가중(×2)이 결제 어휘를 쓰는 글로 쏠린다 |
| 3 | **보류 증가** — 판별기가 걸린 표현을 텍스트에서 지운 뒤 대상 명사를 세는데, "요금"·"구독료"를 신호로 등록하면 그 명사가 지워져 "대상 불분명" 보류가 늘어난다. 정확히 ①이 필요로 하는 글이 사라지는 역효과다 |
| 4 | `PAIN_SIGNALS_TIER2`가 `PAIN_SIGNALS`의 파생값이라 주차별 쿼리 로테이션이 전부 어긋난다 |

그래서 지불 신호는 **판별(3-3)에 쓰지 않고 집계에만 쓴다.** 3-3 통과 여부·`signal_score`·쿼리 조합은 지불 신호를 절대 참조하지 않는다.

| 표현 |
| :-- |
| 돈 아깝, 돈이 아깝, 비용이 아깝, 돈 날렸, 돈 내고, 돈 쓰고, 유료라도, 돈 주고라도, 결제했는데, 구독료, 수수료, 위약금, 환불 안 되, 환불받으려, 환불 절차 |

`"비싸"`(단독은 지불 의사의 반대 신호일 수 있다)·`"요금"`·`"돈 쓰"`(명사 단독, 변별력 없음)·`"환불"`(단독)은 일부러 뺐다 — `DOMAIN_KEYWORDS[금융]`에 이미 `"환불"`이 있어 금융 쿼리로 걸린 글이 자동으로 지불 신호를 갖게 되는 순환 논리가 되기 때문이다.

## 6. 문제로 묶는 기준

PRD 9절 TBD "하나의 문제로 묶는 최소 근거 기준"에 대한 제안이다.
**정기 배치에만 적용된다.** 실시간 탐색 결과는 이 기준을 통과하지 않은 상태로 표시된다.

| 단계 | 조건 | 처리 |
| :-- | :-- | :-- |
| **후보 생성** | 유사한 글 5건 이상 (`settings.MIN_GROUP_SIZE`) | 후보로 등록, 미노출 |
| **게시 가능** | 관련 사례 **20건 이상** + 서로 다른 출처 **3곳 이상** + 근거로 쓸 요약 **3건 이상** | 정식 문제로 노출 |
| **보류** | 사례는 많으나 출처가 1곳 | 노출하지 않음 |

**출처 3곳 조건이 핵심이다.** 한 커뮤니티에서만 100건이 나온 것은
"그 커뮤니티의 화제"이지 "세상의 문제"가 아닐 수 있다.
서로 다른 플랫폼에서 반복되어야 실재하는 문제로 본다.

화면의 `Problem.evidence`는 3~5건만 노출하므로, 묶인 것 중
**서로 다른 출처에서 하나씩** 고르는 것을 기본으로 한다. 한 출처 글만 5개 보여주면
근거가 편중되어 보인다.

> **2026-09-12 구현됨.** "게시 가능" 조건 3개는 `settings.PUBLISH_MIN_CASES`(20)·
> `PUBLISH_MIN_SOURCES`(3)·`PUBLISH_MIN_EVIDENCE`(3)로 구현돼 있고, 근거 조립기(②′
> `EvidenceAgent`)의 `aggregate_tool.publish_gate()`가 판정해 `PublishGate`를 만든다.
> 근거 3~5건 선별(서로 다른 출처에서 하나씩)도 같은 에이전트가 **출처 라운드로빈**으로
> 구현했다(`settings.EVIDENCE_SHOW_MAX`=5). 자세한 것은 `docs/DATA_SPEC.md` 7절.
> 기준 수치(20/3/3)는 실데이터가 쌓인 뒤 조정이 필요한 임시값이다(11절).

## 9. 깨질 때 대비

| 상황 | 대응 |
| :-- | :-- |
| 크롤러가 마크업 변경으로 실패 | 해당 소스만 중단, 나머지는 계속. 실패를 알림으로 남긴다 |
| API 정책·가격 변경 | DATA_SOURCES.md를 갱신하고 대체 소스로 전환 |
| **실시간 중 쿼터 소진** | 코퍼스에 이미 있는 결과만 보여주고, 실시간 수집이 불가함을 표시한다. 숫자를 채워 넣지 않는다 |
| **실시간 응답 지연** | 도착한 플랫폼부터 순차 노출. 전체를 기다리게 하지 않는다 |
| 특정 출처가 과대 대표됨 | 출처별 상한을 두어 한 곳이 `caseCount`의 절반을 넘지 않게 한다 |
| 요약 품질 저하 | 사람이 검수하는 샘플링 큐를 둔다 (초기에는 전수 검수) |

> **초기에는 사람이 검수한다.** 자동 파이프라인이 만든 문제를 그대로 노출하면
> 근거와 서술이 어긋난 문제가 섞인다. MVP 단계에서는 게시 직전에 사람이 본다.
> 다만 **실시간 탐색 결과는 검수를 거칠 수 없다.** 이것이 실시간 결과를
> 정식 문제와 구분해 표시해야 하는 또 하나의 이유다.
