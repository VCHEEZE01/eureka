# 수집·출력 데이터 사양

**팀 목욕중 · 2026-09-09 · 상태: 회의 결과 1차 정리**

화면이 무엇을 보여주는지가 무엇을 수집할지를 결정한다. 이 문서는 그 대응 관계를 못 박는다.

| 문서 | 다루는 것 |
| :-- | :-- |
| [DATA_SOURCES.md](./DATA_SOURCES.md) | **어디서** 가져오나 (플랫폼, API/크롤링, 법적 준수) |
| [DATA_COLLECTION.md](./DATA_COLLECTION.md) | **어떻게·언제** 가져오나 (시점, 쿼리, 판별, 묶기) |
| **이 문서** | **무엇을** 가져와 **무엇을** 보여주나 (필드 단위 대응) |

> 아이디어·개인화 화면(PRD F06~F08)은 ③문제정의·④아이디어 담당 범위라 이 문서에 없다.
> 여기 있는 것은 **수집(①)과 해석(②)에 영향을 주는 것**뿐이다.

## 0. 수집 시점 — 주 1회 배치뿐이다

**사용자의 클릭은 수집을 유발하지 않는다.** 수집은 스케줄러가 주 1회 돌리는 배치 하나뿐이고,
화면은 이미 쌓여 있는 문제 풀을 읽기만 한다.

```
[배치] 주 1회 · 사용자와 무관 · 전체 출처 수집 → 문제 풀을 채움
                     ↓ 읽기만
[화면] 밀리초 · 수집하지 않음 · 쌓인 것을 거르고 보여줌
```

이 결정이 정리하는 것:

| 항목 | 결과 |
| :-- | :-- |
| 온보딩의 출처 선택 | **표시 필터**다. 수집 범위가 아니다. 배치는 항상 전체 출처를 수집한다 |
| 온보딩 진행 상태 UI | 대기가 없으므로 **근거가 사라진다** |
| 실시간 탐색 (`DATA_COLLECTION.md` 1-2절) | **MVP 범위 밖** |
| API 쿼터 | 실시간 몫을 남길 필요가 없다. 배치일 하루치 한도를 다 써도 된다 |
| 5초 응답 목표 | 불필요 |

> `DATA_COLLECTION.md` 1절은 "정기 배치 / 실시간 탐색" 두 축을 정의하지만,
> **MVP는 정기 배치만 구현한다.** 실시간 탐색은 이후 과제로 남긴다.

## 1. 관심분야 설정 (온보딩)

### 관심 키워드 5개

`금융` · `헬스케어` · `라이프스타일` · `IT/생산성` · `교육/커리어` (+ `전체`)

기존 `models.py`의 3개(생산성/업무·커리어/자기계발·라이프스타일)를 대체한다. 프로토타입에 있던 임시 5개는 가상 데이터 기준이므로 무관하다.

### 화면에 뜨는 출처 4개

`뉴스` · `소셜(SNS)` · `블로그` · `공공데이터`

`리뷰`는 쓰지 않는다. **지식iN·카페**는 화면에 띄우지 않되 수집에는 넣을 수 있다 — **미결정 (6절 참조)**.

> **이 선택은 수집 범위가 아니라 표시 필터다** (0절). 배치는 항상 전체 출처를 수집한다.

**필터 동작 — 확정**

| 단계 | 규칙 |
| :-- | :-- |
| **문제를 고를 때** | 근거 중 **하나라도** 선택한 출처에서 나왔으면 그 문제를 목록에 넣는다 |
| **근거를 보여줄 때** | 그 문제의 근거를 **전부** 보여준다. 선택하지 않은 출처의 근거도 함께 나온다 |
| `case_count` · `source_count` | **다시 세지 않는다.** 항상 전체 기준 집계값 |

근거를 출처로 걸러 보여주면 화면의 "관련 사례 128건"과 실제로 보이는 근거 목록이 어긋난다.
전부 보여주면 그 불일치가 없고, 집계를 두 번 할 필요도 없다.

## 4. ★ 불만도·필요도는 점수가 아니라 건수다

`DATA_COLLECTION.md` 7절이 **수치 추정·보정**과 **검증 점수 산출**을 금지한다(PRD F03).
`models.py`도 LLM이 채우는 모델에 숫자 필드를 두지 않는 구조다. "불만도 73점"은 여기 정면으로 걸린다.

**만드는 방식만 바꾸면 원칙을 지키면서 같은 화면이 나온다** — AI는 라벨만 붙이고, 숫자는 DB가 센다.

| 지표 | ❌ 금지 | ✅ 채택 |
| :-- | :-- | :-- |
| **불만도** | AI가 "불만도 73점" 산출 | 근거마다 **불편 강도**(높음/중간/낮음)를 라벨 → **"강한 불만 12건 / 전체 40건"** |
| **필요도** | AI가 "필요도 8.2" 산출 | **결핍 신호**(있었으면·아쉽·없어서·개선됐으면) 등장 여부를 기록 → **"해결책을 원한 언급 17건"** |

필요도는 `DATA_COLLECTION.md` 5절 불편 신호 사전의 **"결핍" 유형**이 그대로 대응된다. 세기만 하면 된다.

**결과적으로 화면의 모든 숫자가 "몇 건"이 된다.** 근거를 눌러 그 12건의 실물을 보여줄 수도 있다.

> ⚠️ 다만 `case_count`는 **순수 DB 집계**이고 "강한 불만 12건"은 **LLM 라벨의 합**이다.
> 성격이 다르므로 화면에서 **"AI가 판정한 건수"임을 구분 표기**해야 한다 (PRD 8절).

## 5. 수집 쪽에 미치는 영향

| 결정 | 수집이 반드시 챙겨야 하는 것 |
| :-- | :-- |
| 유저 한마디 = **실제 발췌** | 인용 가능한 **완결 문장**. 검색 API 스니펫은 조각이라 그대로 못 쓴다 (아래) |
| 일별 언급량 | **`posted_at` (원문 작성일)** — 없으면 그래프에서 빠진다 |
| 출처 URL 노출 | **`url`** + 링크가 실제로 열리는지 |
| 불만도 | ②가 붙이는 **불편 강도 라벨** |
| 필요도 | ②가 기록하는 **결핍 신호 등장 여부** |

### 발췌 재료 — 검색 API 스니펫은 그대로 못 쓴다

네이버·카카오 검색 API가 주는 것은 완결 문장이 아니라 **검색어 주변을 잘라낸 조각**이다.
`<b>` 하이라이트 태그가 섞이고 앞뒤가 `...`로 끊겨 있어 큰따옴표를 붙이면 말이 안 된다.

| 소스 | 발췌 적합성 |
| :-- | :-- |
| **공공데이터 민원·상담사례** | 원문이 정제된 형태. **인용에 가장 안전** |
| **지식iN 질문 제목** | `"회의록 정리 매번 이렇게 번거로운가요?"` — 제목 자체가 완결된 불편 서술 |
| 블로그·뉴스 스니펫 | 문장 단위로 잘릴 때만. 상당수는 버려야 함 |

→ 수집 단계에 **완결 문장 추출기**가 필요하다. 마침표·물음표 기준으로 온전한 문장만 뽑고, 실패하면 그 건은 발췌 후보에서 제외한다.

## 6. 미결정

| # | 항목 | 왜 정해야 하나 |
| --: | :-- | :-- |
| 1 | **지식iN·카페를 수집에 넣는가** | 발췌를 쓰기로 한 이상 사실상 필요하다. 안 넣으면 "유저 한마디" 재료가 공공데이터에 몰린다. 넣으면 "출처 3곳" 조건도 함께 풀린다 |
| 2 | **"서로 다른 출처 3곳"의 정의** | 지식iN/카페/블로그를 3곳으로 셀지, 네이버를 1곳으로 볼지. 후자면 게시 조건이 매우 빡빡해진다 |
| 3 | **일별 언급량의 갱신 주기 표기** | 배치는 주 1회인데 화면은 "7일간"이다. 매일 갱신되는 것처럼 보이지 않게 할지 |
| 4 | **발췌 길이 상한** | `DATA_COLLECTION.md` 3-2는 25자. 화면의 "유저 한마디"에 25자면 충분한지 |
| 5 | **출처 필터의 변별력** | 위 규칙(하나라도 일치 → 통과)에 "출처 3곳 이상"이라는 게시 조건이 겹치면, **대부분의 문제가 어떤 출처를 골라도 통과**할 수 있다. 온보딩 선택이 목록을 실제로 얼마나 바꾸는지는 데이터가 쌓인 뒤 확인해야 한다. 거의 안 바뀌면 온보딩 출처 선택의 존재 이유를 다시 봐야 한다 |

## 7. `models.py` 계약 변경 4건

**③이 DB 스키마를 만들기 전에 공지해야 마이그레이션 재작업이 없다.**

| 대상 | 변경 |
| :-- | :-- |
| `Category` | 3개 → **5개** (금융·헬스케어·라이프스타일·IT/생산성·교육/커리어) |
| `SourceKind` | `리뷰` 제거, **`공공데이터` 추가**. `커뮤니티`는 지식iN·카페용으로 화면 밖에 유지 |
| `RawItem` | `content_hash` · `collected_by` · `license` 추가 (전부 기본값) |
| `Judgement` | **불편 강도 · 결핍 신호 라벨 2개 추가** — 숫자가 아니라 라벨이므로 "LLM은 숫자를 만들지 않는다"는 원칙 유지 |

`RawItem.posted_at`은 타입상 `Optional`이지만 **일별 언급량 때문에 사실상 필수**가 된다.

**`types.ts`는 `Category`·`SourceKind`만 바꾸면 된다.** `RawItem`·`Judgement`·`ProblemCandidate`는 프론트에 노출되지 않는다(프론트가 보는 것은 `Evidence.raw_item_id` 문자열뿐).

## 8. 이 사양에서 새로 생긴 위험

| # | 위험 | 대응 |
| --: | :-- | :-- |
| **1** | **헬스케어·금융의 민감정보** — 건강 경험담은 개인정보보호법상 민감정보일 수 있다. 지금의 PII 제거는 전화·이메일·닉네임 같은 **식별자만** 지우고 병력·투자내역 같은 **내용은 남긴다** | 두 카테고리는 **공공데이터 우선**으로 시작한다. 커뮤니티 원문 수집은 팀·법률 확인 후. **필터가 아니라 소스 선택으로 피한다** |
| **2** | **발췌 인용 범위** — 사용자 글을 상업 서비스 화면에 인용한다. 검색 API 스니펫의 재배포 허용 범위는 `DATA_SOURCES.md` 8절에 미결정으로 남아 있다 | 길이 상한 엄수 · 출처명과 링크 병기 · 소스별 약관 확인 후 `license` 플래그로 게이팅 |
| **3** | **일별 그래프 왜곡** — 검색 API가 최신순(`sort=date`)이라 **수집 직전 며칠에 글이 몰린다.** 주 1회 배치가 확정됐으므로 그래프는 **주 1회만 갱신되고**, 일별 분포는 실제 언급 추세가 아니라 수집 시점의 그림자에 가깝다 | 구조적 문제다. 배치 주기를 올리거나 화면 문구를 바꾸는 **팀 결정**이 필요하다. 지금 형태로는 "7일 추세"라고 부르기 어렵다 |
| **4** | **출처 다양성** — 화면 출처 4종 중 소셜은 Threads뿐이고 권한 승인 대기다. 실질 3종으로 시작한다 | 공공데이터를 초반에 붙인다 |
