## 0. 수집 시점 — 타겟 입력에 따른 수집 요청

**2026-09-13 사용자 변경 결정.** 온보딩의 나이대·성별·직업·장소는 실제 수집 조건이다.
사용자가 문제 정의 탐색을 요청하면 입력값에 맞는 검색어로 수집하고, 그 실행에서 얻은 근거로 문제정의·상세 데이터를 만든다.
기존의 “주 1회 배치만 실행하며 사용자 클릭은 수집을 유발하지 않는다” 결정은 이 사용자 경로에 더 이상 적용하지 않는다.

```text
[온보딩] 네 항목 중 최소 두 항목 → [탐색 요청] 타겟을 고정한 수집 실행
 → 검색 API → 정제·불편 판별 → 묶기·근거 집계 → 문제정의·AI 검수
 → 해당 실행의 결과·근거 상세 (게시 기준 및 검수 상태 표시)
```

- 조회 요청 자체는 수집을 시작하지 않는다. 탐색 요청과 진행 상태 조회를 분리한다.
- 타겟을 바꾸면 다른 실행으로 취급한다. 이전 타겟의 자료를 이번 수집 결과로 섞지 않는다.
- 검색어에 조건이 포함된 것은 작성자가 그 속성을 가졌다는 증거가 아니다. 제목·스니펫에서 입력 필드의 문구가 모두 확인된 자료만 판별에 넣는다(직업·장소 목록은 각각 하나 이상). 미확인 자료는 보존하되 타겟 문제 생성에서 제외한다. 문구 동시 등장은 작성자 속성 검증이 아니며, 연령·성별 집계는 원문의 명시적 자기 서술만 사용한다.
- 수집·판별·검수의 실제 상태를 표시하며, 고정 타이머를 수집 진행률로 표시하지 않는다.
- 자료 없음, 검색 실패, 생성 실패, 게시 기준 미달은 구분한다. 아이디어·조합·개인화는 잠금 상태다.
- 주간 배치 코드는 별도 경로로 보존한다. 실행 시각·운영 주기·트래픽별 비용 배분은 아직 확정하지 않았다.

검색 조합과 호출 상한 등 구현 선택 및 검증 기록은 [타겟 수집 실행 안내](TARGET_COLLECTION_RUNBOOK.md)에 기록한다.

## 1. 타겟 설정 (온보딩)

**2026-09-12 사용자 최종 결정.** 카테고리·플랫폼 선택은 제거하고 사용자가
문제를 찾고 싶은 타겟의 나이대·성별·직업·장소를 입력한다.

| 항목 | 입력 형태 | 선택지·동작 |
| :-- | :-- | :-- |
| 나이대 | 드롭다운 | 미선택·10대·20대·30대·40대·50대 이상 |
| 성별 | 드롭다운 | 미선택·여성·남성 |
| 직업 | 키워드 입력 | 입력 후 Enter로 칩 등록, 칩의 ×로 삭제 |
| 장소 | 키워드 입력 | 입력 후 Enter로 칩 등록, 칩의 ×로 삭제 |

- 나이대 선택, 성별 선택, 직업 키워드 1개 이상, 장소 키워드 1개 이상을 각각
  하나의 입력 항목으로 센다. 네 항목 중 **최소 2개**가 채워져야 문제 정의 탐색이 가능하다.
- 0~1개 입력 상태에서는 버튼을 비활성화하고, 탐색을 시도하면 비어 있는 필드를
  표시하며 최소 2개 입력을 안내한다.
- 직업·장소는 각각 최대 5개까지 등록하며 중복 키워드는 추가하지 않는다.
- 선택값은 공유용 HTML의 `localStorage.eureka_target_profile`에 저장하고
  수집 요청과 결과 화면 조건 요약에 전달한다. 카테고리·플랫폼 선택을 되살리지 않으며, 결과는 해당 타겟 수집 실행에 속한 자료로 구성한다.
- 근거와의 타겟 대조는 AI 서술이 아니라 `Evidence.summary`만 대상으로 한다. 이 대조 표시는 수집 조건 적용과 별도이며, 대조만으로 작성자 속성이 확인됐다고 표시하지 않는다.

## 3. 문제 상세 — 근거 상세 페이지 (2026-09-12 8블록으로 확장)

`ProblemSignals`·`PublishGate`(둘 다 `models.py`)가 이 절의 정본이다. 문제 상세 페이지는 "이 문제를 믿어도 되는가"를 8개 블록으로 답한다.

| 블록 | 화면 제목 | 채우는 것 | 성격 |
| :-- | :-- | :-- | :-- |
| ⑧ | 이 문제를 믿어도 되는가 | `Problem.gate`(게시 기준 체크리스트) + `signals.source_kind_counts`·`source_name_counts` | DB 집계 |
| ④ | 얼마나 꾸준히 나타나나 | `signals.weekly_counts`·`observed_weeks`·`undated_count` | DB 집계 — "화제성"이라 부르지 않는다 (8절 위험 3) |
| ⑦ | 얼마나 불편해하나 | `signals.severity_counts` + `severity_labeled_count`(분모) · `need_signal_count` | ②라벨의 합. **[AI 판정] 표기 필수** |
| ① | 돈이 걸린 문제인가 | `signals.payment_signal_count` | 규칙 집계(`PAYMENT_SIGNALS`), DB 집계 |
| ⑤ | 누가 겪고 있나 | 주력: `source_kind_counts` / 보조: `role_counts`·`age_counts`·`gender_counts` + 각 분모 · 타겟 대조(1절) | 보조는 **[AI 판정]**, 표본 3건 미만이면 숨김 |
| ② | 이미 나와 있는 것들 | `signals.mentioned_services` | ②라벨(원문 verbatim 검증). **'리뷰 불만'은 아니다** |
| ⑥ | 왜 이런 문제가 생겼나 | `Problem.context` | AI 서술 |
| ③ | 만들기에 얼마나 복잡한가 | `Problem.complexity_note` | AI 서술. **점수·등급 금지** |

과거 이 표에 있던 "일별 언급량(7일)"·"유저 한마디(카드 단위)"는 위 8블록으로 흡수됐다. 발췌(`Evidence.excerpt`)는 8절 위험 2(인용 범위 미결정)가 풀리기 전까지 대부분 `null`이다 — 근거 상세는 발췌 없이 요약(`Evidence.summary`)만으로도 성립하도록 설계했다.

근거 목록은 `[전체] [강한 불만] [돈 언급] [해결책 탐색]`으로 필터링한다.
이를 위해 `Evidence`가 원본 `Judgement`의 `severity`·`has_payment_signal`·
`has_need_signal` 라벨을 그대로 보존한다. 새 숫자를 만들거나 집계값을 복제하지 않는다.

### 원안에서 바꾼 항목 3개 — 근거 있음

- **① 돈**: "사람들이 돈을 쓰는 문제인가"(지불 의사, 추정)가 아니라 "돈 얘기가 나왔는가"(사실)만 센다.
- **② 유사 서비스**: "유사 서비스 유무 및 리뷰 불만"에서 **리뷰를 뺐다.** `SourceKind`에 리뷰가 없다(0절 이전 버전 참고, 지금은 `뉴스`·`소셜`·`블로그`·`공공데이터`·`커뮤니티` 5종). 앱스토어 리뷰 RSS는 `DATA_COLLECTION.md` 4-3절에 설계는 있으나 미착수 — 추가는 팀 결정 사항.

## 4. ★ 불만도·필요도는 점수가 아니라 건수다

`DATA_COLLECTION.md` 7절이 **수치 추정·보정**과 **검증 점수 산출**을 금지한다(PRD F03).
`models.py`도 LLM이 채우는 모델에 숫자 필드를 두지 않는 구조다. "불만도 73점"은 여기 정면으로 걸린다.

**만드는 방식만 바꾸면 원칙을 지키면서 같은 화면이 나온다** — AI는 라벨만 붙이고, 숫자는 DB가 센다.

| 지표 | ❌ 금지 | ✅ 채택 |
| :-- | :-- | :-- |
| **불만도** | AI가 "불만도 73점" 산출 | 근거마다 **불편 강도**(높음/중간/낮음)를 라벨 → **"강한 불만 12건 / 전체 40건"** |
| **필요도** | AI가 "필요도 8.2" 산출 | **결핍 신호**(있었으면·아쉽·없어서·개선됐으면) 등장 여부를 기록 → **"해결책을 원한 언급 17건"** |

필요도는 `DATA_COLLECTION.md` 5절 불편 신호 사전의 **"결핍" 유형**이 그대로 대응된다. 세기만 하면 된다.

**결과적으로 화면의 모든 숫자가 "몇 건"이 된다.** 근거를 눌러 그 12건의 실물을 보여줄 수도 있다.

> ⚠️ 다만 `case_count`는 **순수 DB 집계**이고 "강한 불만 12건"은 **LLM 라벨의 합**이다.
> 성격이 다르므로 화면에서 **"AI가 판정한 건수"임을 구분 표기**해야 한다 (PRD 8절).

**⑧ 블록의 게시 기준 체크리스트가 이 원칙의 화면판이다.** `Problem.gate`(`PublishGate`)는 관련 사례·서로 다른 출처·근거 요약 각각이 기준 수치를 넘었는지를 실제 집계값과 함께 보여준다. 판정 당시의 기준도 `min_cases`·`min_sources`·`min_evidence`에 담아 프론트 하드코딩 없이 함께 표시한다 — 지어낸 신뢰 점수 대신 **미리 정해둔 기준을 실제로 넘었다는 사실**을 보여주는 방식이다 (`DATA_COLLECTION.md` 6절, `settings.PUBLISH_MIN_*`).

## 5. 수집 쪽에 미치는 영향

| 결정 | 수집이 반드시 챙겨야 하는 것 |
| :-- | :-- |
| 유저 한마디 = **실제 발췌** | 인용 가능한 **완결 문장**. 검색 API 스니펫은 조각이라 그대로 못 쓴다 (아래) |
| 일별 언급량 | **`posted_at` (원문 작성일)** — 없으면 그래프에서 빠진다 |
| 출처 URL 노출 | **`url`** + 링크가 실제로 열리는지 |
| 불만도 | ②가 붙이는 **불편 강도 라벨** |
| 필요도 | ②가 기록하는 **결핍 신호 등장 여부** |

### 발췌 재료 — 검색 API 스니펫은 그대로 못 쓴다

네이버·카카오 검색 API가 주는 것은 완결 문장이 아니라 **검색어 주변을 잘라낸 조각**이다.
`<b>` 하이라이트 태그가 섞이고 앞뒤가 `...`로 끊겨 있어 큰따옴표를 붙이면 말이 안 된다.

| 소스 | 발췌 적합성 |
| :-- | :-- |
| **공공데이터 민원·상담사례** | 원문이 정제된 형태. **인용에 가장 안전** |
| **지식iN 질문 제목** | `"회의록 정리 매번 이렇게 번거로운가요?"` — 제목 자체가 완결된 불편 서술 |
| 블로그·뉴스 스니펫 | 문장 단위로 잘릴 때만. 상당수는 버려야 함 |

→ 수집 단계에 **완결 문장 추출기**가 필요하다. 마침표·물음표 기준으로 온전한 문장만 뽑고, 실패하면 그 건은 발췌 후보에서 제외한다.

새로 생긴 신뢰 개념 하나: **근거 조립기(②′ `EvidenceAgent`)**가 ②(해석기)와 ③(문제정의 생성기) 사이에 들어온다. 근거 선별·신호 집계·게시 기준 판정을 전담하고, `llm_tool`을 import하지 않는다 — "AI는 라벨만, 숫자는 DB가"를 파일 경계로 강제한다. 자세한 것은 `Final/Backend/app/agents/evidence_agent.py` 머리말 참고.

**`api/types.ts`는 두 차례 모두 백엔드와 1:1로 동기화됐다** (스네이크 케이스 유지). `RawItem`·`Judgement`·`ProblemCandidate`·`EvidenceBundle`은 여전히 프론트에 노출되지 않는다 — 프론트가 보는 것은 `Problem`(now `signals`·`gate` 포함)과 `Evidence`뿐이다.
