## 관찰

유저 테스트에서 두 가지가 나왔다.

1. **"개인화라지만 그냥 카테고리 선택 같다."** 조건(연령·성별·직업·장소)을 입력해도, 결과가 내 상황의 문제가 아니라 분야별 일반 문제로 읽혔다.
2. **문제 상세의 근거가 약하다.** "유레카"를 외칠 만큼 이 문제가 중요하다고 설득되지 않았다.

두 숙제의 처방은 같아 보였다 — **더 많이, 더 깊게 수집한다.**

## 시도

수집량 확대를 시도했고, 포텐스닷 API와 Gemini 무료 호출 API의 **시간·비용 한계**에 부딪혔다.

## 측정

타겟 `20대 / 남성`으로 실행한 run `col-19b35025dfde404b84ae8a03` 기준.

| 단계 | 소요 | 비중 |
|---|---|---|
| 검색 (120쿼리, 성공률 100%) | 14초 | 2% |
| **LLM 판별** | **10분 59초** | **96%** |
| 근거 연결 + 문제정의 생성 | 3초 | 2% |
| **합계** | **11분 16초** | |

퍼널:

```
신규 저장 1,191건
  └─ 판별 1,187건 (판별 실패 0건)
       └─ "불편이다"      101건  ← 8.5%
            └─ "타겟 연결"   1건  ← 1.0%
                 └─ 문제정의 1개 (검수: 보류)
```

- 전환율 **0.084%**
- 탈락 사유: 타겟 미확인 **1,186** / 불편 아님 1,039 / 정보 부족 47 / 규칙 필터 4
- 전체 검색 카탈로그 26,136개 중 소화 120개 = **0.46%** → 전량 환산 시 약 40시간 · LLM 호출 약 14,000회

## 발견

판별 LLM에 들어가는 텍스트는 두 줄이 전부였다.

```python
# app/tools/llm_tool.py:210
text = f"{item.title} {item.snippet}"
```

저작권 정책상 원문 본문을 저장하지 않고 검색 요약만 보관하는 구조였다. 그 두 줄로 **"이 글을 쓴 사람이 20대 남성인가"**를 판정하라고 요구한 셈이다. 판별 실패 0건에 미확인 1,186건이라는 결과는 모델의 실패가 아니라 **질문 자체가 성립하지 않는다는 증거**다.

여기서 유저 테스트의 두 숙제가 같은 뿌리였음이 드러난다.

| 사용자가 느낀 것 | 실제 원인 |
|---|---|
| "카테고리 선택 같다" | 타겟이 반영된 건 1,191건 중 1건. 시스템이 개인 조건을 반영할 수 없으니 남는 구분은 카테고리뿐 |
| "근거가 와닿지 않는다" | 근거로 쓸 재료가 스니펫 두 줄. 근거 페이지가 빈약한 게 아니라 재료가 빈약했다 |

**개인화가 부족했던 게 아니라, 수집한 데이터로는 개인화가 성립할 수 없었다.** 그리고 처방이었던 "더 많이 수집"은 비용만 선형으로 키우고 전환율은 그대로 두는 선택이었다.

## 결정

v0 파이프라인을 폐기한다. 튜닝 대상이 아니라 **전제가 틀린 설계**다.

| | v0의 전제 | 실측 |
|---|---|---|
| 병목 | 수집량 | 건별 LLM 판별 (96%) |
| 확장 전략 | 더 많이 수집 | 비용만 선형 증가, 품질 정체 |
| 개인화 | 스니펫으로 타겟 판별 가능 | 1,186/1,187 미확인 — 관측 불가 |
| 산출 효율 | — | 1,191건 → 1건 (0.084%) |

## v1 방향

**트렌드 키워드와 사람들이 꾸준히 검색하는 키워드를 미리 확보해 두고, 그 키워드로 아이디어를 생성한 뒤, 바이브코딩으로 직접 만들어볼 수 있게 돕는다.**

```
v0   사용자 입력 → 실시간 대량 수집 → 건별 LLM 판별 → 문제정의
     └ 런타임 비용 폭발 · 11분 대기 · 전환율 0.084%

v1   [사전] 트렌드·검색 키워드 확보
     [런타임] 키워드 → 아이디어 생성 → 바이브코딩으로 실행
     └ 비용을 런타임에서 배치로 이동 · 즉시 응답
```

| v0의 문제 | v1의 해법 |
|---|---|
| 스니펫으로 개인을 추론 (불가능) | **검색량**이라는 관측 가능한 신호를 사용 — 추론이 필요 없다 |
| 11분 대기 | 키워드 사전 확보로 런타임 비용 최소화 |
| 수집량에 비례하는 API 비용 | 사전 배치로 분리 · 예측 가능 |
| 근거가 스니펫 두 줄 | "실제로 사람들이 계속 검색한다"가 근거 자체 |

v0은 **문제를 찾아주는 데서 끝났고**, 사용자에게 "그래서 뭘 하지?"가 남았다. v1은 **만들어보는 데까지 연결한다.** 유레카의 순간을 문제를 발견할 때가 아니라 **직접 만든 것이 동작할 때**로 옮긴다.
