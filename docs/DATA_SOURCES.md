# 데이터 소스 정리

유레카의 문제 데이터 생성 파이프라인(PRD F00)에 쓸 수집처 후보를 정리한다.
PRD 8절 "문제 데이터 출처"와 9절 TBD "실제 사용할 외부 데이터 소스" 결정을 위한 문서다.

**조사 기준일: 2026-09-02.** API 가격·정책은 자주 바뀌므로 착수 직전 재확인이 필요하다.

## 범위 원칙

- **국내 플랫폼을 대상으로 한다.** 유레카의 타깃이 한국 메이커이므로 한국어 불편 데이터가 우선이다.
- **해외 플랫폼은 현재 제외**하되 [7절 부록](#7-부록--해외-플랫폼-현재-제외)에 따로 정리해 둔다. 해외 확장 시 재검토한다.
- YouTube·App Store처럼 **운영사는 해외지만 한국 이용자 데이터를 얻을 수 있는 것**은 국내로 분류한다.
  로케일·언어 필터로 한국어 콘텐츠만 수집할 수 있기 때문이다.

---

## 1. 분류 기준

수집처를 **A. 공식 API 발급 가능** / **B. API 없음 → 크롤링 검토** 두 갈래로 나눈다.

| 기준 | 내용 |
| :-- | :-- |
| 공식 경로 존재 | 사업자가 제공하는 API·피드·공개 데이터셋이 있는가 |
| 이용약관 | 수집·저장·2차 가공이 약관상 허용되는가 |
| 접근 제약 | 로그인·회원제·봇 차단이 있는가 (있으면 우회하지 않고 제외) |

**원칙: A가 가능하면 항상 A를 쓴다.** B는 A로 대체 불가능하고 데이터 가치가 확실할 때만 검토한다.

## 2. A. 공식 API 발급이 가능한 플랫폼 (국내)

### 2-1. 검색 — 가장 넓은 커버리지

| 플랫폼 | 얻는 데이터 | 발급 | 한도 | 비용 |
| :-- | :-- | :-- | :-- | :-- |
| **네이버 검색 오픈API** | 블로그, **카페글**, **지식iN**, 뉴스, 웹문서, 쇼핑, 지역, 책 | 개발자센터 앱 등록 | 일 25,000회 | 무료 |
| **카카오 다음 검색 API** | 웹문서, 블로그, **카페**, 동영상, 이미지, 책 | Kakao Developers 앱 등록 | 웹문서 일 30,000건 (API별 상이) | 무료 |

> 두 검색 API가 이 프로젝트의 **중심축**이다. 특히 네이버 지식iN과 카페글은
> "이런 게 불편한데 방법 없나요" 형태의 원문이 그대로 쌓여 있어 문제 발굴에 가장 적합하다.
> 네이버와 카카오를 **둘 다 쓰면 서로 다른 커뮤니티 풀**을 덮을 수 있다.
>
> 다만 검색 API는 **스니펫(제목·요약·링크)** 중심이다. 본문 전체가 필요하면 별도 판단이 필요한데,
> PRD F03이 어차피 "원문 전체 복제 대신 요약 기본"이므로 스니펫만으로도 상당 부분 충족된다.

### 2-2. 추세 신호 — PRD의 "언급량·추세"에 직결

| 플랫폼 | 얻는 데이터 | 발급 | 비고 |
| :-- | :-- | :-- | :-- |
| **네이버 데이터랩 API** | 통합 검색어 트렌드, 쇼핑인사이트 | 네이버 개발자센터 (검색 API와 동일 계정) | 절대 검색량이 아니라 **상대 지수**를 준다. "이 문제가 늘고 있는가"의 근거로 쓸 수 있으나, 절대 수치처럼 표시하면 PRD의 "근거 없는 수치 생성 금지"에 어긋난다 |

### 2-3. 공공데이터 — "실제 불편"에 가장 가까운 원천

민원·소비자 상담은 성격상 **불편 그 자체**라 유레카와 잘 맞는다. 모두 무료이며 활용 신청이 필요하다.

| 소스 | 얻는 데이터 | 비고 |
| :-- | :-- | :-- |
| **국민권익위 민원빅데이터 분석정보 API** | 국민신문고·지자체 민원·제안 분석 정보 | 원문이 아니라 **분석 정보**라는 점에 주의. 실제 제공 필드 확인 필요 |
| **한국소비자원 Open API** | 소비자 상담사례, 피해구제, 분쟁조정, 기타민원 | 라이프스타일·소비 카테고리에 직접 대응 |
| **빅카인즈 (한국언론진흥재단)** | 100여 개 언론사 뉴스 | 이용 조건과 **상업적 활용 범위 확인 필요** |
| **AI 허브 (NIA)** | 민간 민원 상담 등 한국어 데이터셋 | API가 아닌 **일회성 다운로드**. 본인 확인·목적 명시 후 이용. 파이프라인 소스가 아니라 초기 부트스트랩·모델 참고용으로 적합 |
| **공공데이터포털 전반** | 부처·지자체 데이터셋 | 위 항목 외에 쓸 만한 게 더 있는지 **조사 필요** |

### 2-4. 리뷰 — 글로벌 플랫폼의 한국 데이터

| 플랫폼 | 얻는 데이터 | 발급 | 한도 | 비고 |
| :-- | :-- | :-- | :-- | :-- |
| **YouTube Data API v3** | 한국어 영상 댓글 | Google Cloud 프로젝트 | 일 10,000 units | `commentThreads.list` 1 unit, `search.list` 100 units — **검색은 아끼고 댓글을 많이 파는 설계**가 유리 |
| **App Store 고객 리뷰 RSS** | 한국 스토어 앱 리뷰 (경쟁 앱 포함) | 불필요 | 명시 없음 | 공개 RSS라 자사 앱 제한이 없다 |

> **주의**: App Store **Connect** API와 Google Play Developer API는 **자사 앱만** 조회할 수 있다
> (플레이는 최근 7일 제한). 타사 앱 리뷰가 필요하면 A가 아니라 B다.
> App Store는 위 공개 RSS라는 우회로가 있지만, Google Play는 없다.

### 2-5. SNS — 사실상 Threads 하나

SNS는 대부분 공식 경로가 막혀 있다. **합법적으로 쓸 수 있는 것은 Threads가 거의 유일하다.**

| 플랫폼 | 얻는 데이터 | 발급 | 한도 | 비용 |
| :-- | :-- | :-- | :-- | :-- |
| **Threads (Meta)** | **공개 게시물 키워드·토픽 태그 검색** (TOP/RECENT, 기간 지정 가능) | `threads_basic` + **`threads_keyword_search` 권한 승인 필요** | **7일 롤링 500쿼리** | 무료 |

> - 권한 승인 **전에는 본인 게시물만** 검색된다. 승인이 나야 공개 게시물을 볼 수 있다.
> - **7일에 500쿼리는 매우 빡빡하다.** 키워드를 엄선해 주 단위 배치로 돌리는 설계가 필요하다.
>   상시 수집이 아니라 "이미 후보로 잡은 문제의 언급 여부 확인"에 쓰는 편이 현실적이다.
> - 국내 이용자 기반이 커지고 있어 텍스트 기반 불만이 쌓이는 곳이다. **승인 신청을 먼저 넣어 둘 가치가 있다.**

**다른 SNS가 막힌 이유**

| 플랫폼 | 상태 |
| :-- | :-- |
| **Instagram** | Graph API가 **비즈니스/크리에이터 계정 한정**. 2024년에 로그아웃 상태 해시태그·키워드 탐색이 제거됐다. 광범위 수집 불가 |
| **TikTok** | Research API는 **미국·EU 등 학술 기관 전용이며 상업적 이용을 명시적으로 금지**한다. 승인 4주, 일 1,000요청. 우리는 대상이 아니다 |
| **X (Twitter)** | 신규 무료 티어 없음 → [7절 부록](#7-부록--해외-플랫폼-현재-제외) |
| **Facebook** | 공개 데이터 수집 경로가 연구자용으로 한정됨 |

## 3. B. 공식 API가 없어 크롤링을 검토해야 하는 플랫폼 (국내)

크롤링은 법적 위험이 실재한다([5절](#5-크롤링-시-반드시-지킬-것) 참고).
위험도는 **접근 제약과 약관** 기준이며, 실제 착수 전 사이트별 robots.txt와 약관을 개별 확인해야 한다.

### 3-6. SNS 크롤링을 다시 본다면

"SNS는 약관상 금지"라고만 정리하는 것은 부정확하다. 실제로는 **법적 문제와 기술적 문제가 다르고,
우리에게 실질적인 차단 요인은 법이 아니라 기술 쪽**이다.

**(1) 법적으로는 생각보다 열려 있다 — 단, 미국 기준이다**

2024년 1월 **Meta v. Bright Data** (미 캘리포니아 북부지법)에서 법원은
**로그아웃 상태로 공개 데이터를 수집하는 행위에는 Meta의 이용약관이 적용되지 않는다**고 판단했다.
로그아웃 상태에서는 페이스북·인스타그램의 "user"가 아니므로 약관에 구속되지 않는다는 논리다.
페이스북 약관의 영구 금지(survival) 조항도 집행 불가로 봤고, 인스타그램에는 그 조항조차 없다고 지적했다.
**Meta는 이후 소를 취하했다.**

다만 이것을 근거로 삼기엔 한계가 분명하다.

- **미국 지방법원 판결이다.** 국내법에 그대로 적용되지 않는다.
- 국내에서는 **개인정보보호법**이 별도로 걸린다. 공개된 개인정보라도 정보주체의 자기결정권이 사라지지 않는다.
- 국내 판례(사람인, 엔하위키 미러)는 **무단 크롤링에 대해 일관되게 엄격**하다.

**(2) 실질적인 차단 요인은 로그인 장벽이다**

인스타그램은 **2024년에 로그아웃 상태의 해시태그·키워드 탐색을 제거**했다.
즉 Bright Data 판결이 허용한 "로그아웃 공개 수집"으로는 **볼 수 있는 것이 거의 없다.**
의미 있는 양을 모으려면 로그인해야 하고, 로그인하는 순간 약관 적용 대상이 되어
우리 원칙("로그인이 필요한 곳은 크롤링하지 않는다")과 정면으로 충돌한다.

여기에 봇 탐지, 계정 차단, 레지덴셜 프록시 비용까지 붙는다.
**즉 인스타 크롤링은 "하면 안 되는 일"이라기보다 "해도 잘 안 되고, 되게 하려면 선을 넘어야 하는 일"에 가깝다.**

**(3) 제품 관점에서 우선순위가 낮다**

법·기술을 떠나 유레카에 얼마나 쓸모 있는지도 봐야 한다.

| | 인스타그램 | 텍스트 커뮤니티 |
| :-- | :-- | :-- |
| 콘텐츠 형태 | **이미지·영상 중심**, 캡션은 짧고 해시태그 위주 | 긴 서술형 본문 |
| 불편 서술 밀도 | 낮음 | **높음** ("이런 게 불편한데 방법 없나요") |
| 수집 난이도 | 높음 (로그인·봇 탐지·프록시) | 낮음 |
| 개인정보 위험 | 높음 (계정·얼굴·위치) | 상대적으로 낮음 |

같은 공수를 네이트판·뽐뿌·클리앙에 쓰면 **훨씬 많은 문제 서술을 얻는다.**

**(4) 결론**

| 대상 | 판단 |
| :-- | :-- |
| 인스타그램 | **MVP 제외.** 로그인 없이는 데이터가 안 나오고, 로그인하면 원칙 위반. 이미지 중심이라 회수도 낮다 |
| 틱톡 | **MVP 제외.** Research API는 학술 전용·상업 금지, 크롤링은 인스타와 동일한 문제 |
| **Threads** | **여기가 답이다.** 텍스트 중심 SNS이고 **공식 키워드 검색 API가 있다** ([2-5절](#2-5-sns--사실상-threads-하나)). SNS 데이터가 필요하면 크롤링이 아니라 이 경로를 쓴다 |

> SNS를 꼭 넣어야 한다면 **Threads 권한 승인을 먼저 신청**하는 것이 유일하게 깨끗한 길이다.
> 인스타·틱톡은 정책이 바뀌거나 상업용 API가 열릴 때 다시 본다.

## 4. 두 방식 비교

| | A. 공식 API | B. 크롤링 |
| :-- | :-- | :-- |
| 안정성 | 스키마 보장, 변경 시 공지 | 마크업 변경에 그대로 깨짐 |

| 커버리지 | 제공 범위로 한정 (검색 API는 스니펫 위주) | 원하는 곳을 넓게, 본문까지 |
| 비용 | 국내 주요 API는 무료 | 인프라 + 유지보수 인건비 |
| 착수 속도 | 빠름 (키 발급) | 느림 (사이트별 구현) |

## 5. 크롤링 시 반드시 지킬 것

국내에 **대법원 판례**가 있다. 잡코리아 채용정보를 사람인이 크롤링해 자사 서비스에 사용한 사건에서
법원은 **데이터베이스권 침해 및 부정경쟁행위**로 판단해 369건에 대해 건당 50만 원,
총 1억 9,800만 원 배상을 명했다.

판결에서 불리하게 작용한 요소가 그대로 우리의 준수 사항이 된다.

| 판례에서 문제가 된 행위 | 우리가 지킬 것 |
| :-- | :-- |
| robots.txt를 확인조차 하지 않음 | **robots.txt를 읽고 준수한다** |
| IP 차단을 VPN으로 우회 | **차단되면 중단한다. 우회하지 않는다** |
| 정체를 숨기고 접근 | **User-Agent에 서비스명·연락처를 명시한다** |
| 무차별 복제 후 출처 삭제 | **요약 중심으로 저장하고 출처를 반드시 표시한다** |

추가로 지킬 것:

- **요청 간 지연**을 두어 상대 서버에 부담을 주지 않는다.
- **원문 전량 저장 금지.** PRD F03 정책과 동일하게 요약을 기본으로 하고, 허용된 경우에만 짧은 발췌와 원문 링크를 남긴다.
- **개인정보를 수집·저장하지 않는다.** 작성자 ID·닉네임은 저장 대상에서 제외한다.
- 수집 시각·출처 URL·라이선스 상태를 **레코드마다 함께 기록**한다.

## 6. MVP 1차 조합 제안

PRD의 초기 카테고리(생산성/업무, 커리어/자기계발, 라이프스타일)를 덮는 최소 조합이다.

| 순서 | 소스 | 방식 | 채우는 카테고리 | 이유 |
| :-- | :-- | :-- | :-- | :-- |
| 1 | 네이버 검색 API (지식iN·카페글·블로그) | A | 전체 | 한국어 불편 데이터의 폭이 가장 넓다. 무료·즉시 |
| 2 | 카카오 다음 검색 API | A | 전체 | 네이버가 못 덮는 풀을 보완 |
| 3 | 한국소비자원 / 국민권익위 민원 API | A | 라이프스타일 | 불편이 이미 정제된 형태로 존재 |
| 4 | YouTube 댓글 + App Store 리뷰 RSS | A | 라이프스타일, 생산성 | 제품 사용 중 불편이 구체적으로 드러남 |
| 5 | Threads 키워드 검색 API | A | 전체 | 권한 승인에 시간이 걸리므로 **신청만 미리 넣어 둔다** |
| 6 | 디스콰이엇, 긱뉴스, OKKY | B | 생산성/업무, 커리어 | 메이커·개발자 데이터는 크롤링 외에 경로가 없다 |
| 7 | 네이트판, 뽐뿌, 클리앙 | B | 라이프스타일 | 종합 커뮤니티 중 문제 서술 밀도가 가장 높은 셋 |

**1~4(전부 A)만으로 먼저 파이프라인을 완성하고**, 데이터가 부족한 카테고리에 한해 6~7을 추가하는 순서를 제안한다.
크롤링을 나중으로 미루면 법적 검토 시간을 벌 수 있고 초기 구현 속도도 빨라진다.
5(Threads)는 승인 대기가 있으므로 **1번과 동시에 신청**해 두는 편이 좋다.

> **생산성/업무·커리어 카테고리는 A만으로 채워지지 않는다.** 이 카테고리의 원천(디스콰이엇, OKKY,
> 긱뉴스 등)은 전부 크롤링 대상이라, MVP에서 세 카테고리를 균등하게 채우려면 6번이 필수가 된다.
> 카테고리를 줄여서 A만으로 출시할지, 6번까지 포함할지는 팀 결정이 필요하다.

## 7. 부록 — 해외 플랫폼 (현재 제외)

지금은 쓰지 않는다. **제외 사유는 "쓸모없어서"가 아니라 타깃 불일치와 비용**이다.
해외 확장 또는 영어권 문제 발굴이 필요해지는 시점에 이 표부터 다시 본다.

| 플랫폼 | 방식 | 조건 | 제외 사유 |
| :-- | :-- | :-- | :-- |
| **Hacker News (Algolia API)** | A | 무료, **키 불필요, 사실상 무제한** | 접근성은 가장 좋다. 영어권 개발자 한정이라 타깃 불일치. **해외 확장 시 1순위** |
| **Reddit Data API** | A | 무료 티어 OAuth 100 QPM이나 **비상업 전용**. 상업 $0.24/1k calls. 수동 승인 2~4주, 거절 가능 | 상업 이용 시 비용·승인 리스크. 날짜 범위 검색·댓글 검색 불가, 리스팅 1,000건 상한 |
| **X (Twitter) API** | A | **신규 무료 티어 없음.** 2026-02-06부터 pay-per-use 기본, 읽기 $0.005/post, 월 200만 건 상한 | 비용이 가장 큰 장벽 |
| **Product Hunt** | A | GraphQL API (조건 **확인 필요**) | 제품 출시 반응 파악에는 좋으나 "불편" 원천으로는 약함 |
| **Stack Overflow (Stack Exchange API)** | A | 무료, 쿼터 있음 (**확인 필요**) | 기술 질문 편중 |
| **Trustpilot / G2** | A/B | 상업 API는 유료 | B2B SaaS 불만 파악용. 국내 커버리지 거의 없음 |
| **Indie Hackers / Quora** | B | 공식 API 없음 | 영어권 한정 |
| **Discord** | A | Bot API. 서버 초대 필요 | 공개 수집 대상이 아님 |
