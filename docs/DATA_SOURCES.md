# 데이터 소스 정리

유레카의 문제 데이터 생성 파이프라인(PRD F00)에 쓸 수집처 후보를 정리한다.
PRD 8절 "문제 데이터 출처"와 9절 TBD "실제 사용할 외부 데이터 소스" 결정을 위한 문서다.

**조사 기준일: 2026-09-02.** API 가격·정책은 자주 바뀌므로 착수 직전 재확인이 필요하다.
특히 Reddit과 X는 최근 2년 사이 두 번 이상 정책이 바뀌었다.

---

## 1. 분류 기준

수집처를 **A. 공식 API 발급 가능** / **B. API 없음 → 크롤링 검토** 두 갈래로 나눈다.
갈래를 정하는 기준은 아래 세 가지다.

| 기준 | 내용 |
| :-- | :-- |
| 공식 경로 존재 | 사업자가 제공하는 API·피드·공개 데이터셋이 있는가 |
| 이용약관 | 수집·저장·2차 가공이 약관상 허용되는가 |
| 접근 제약 | 로그인·회원제·봇 차단이 있는가 (있으면 우회하지 않고 제외) |

**원칙: A가 가능하면 항상 A를 쓴다.** B는 A로 대체 불가능하고 데이터 가치가 확실할 때만 검토한다.

---

## 2. A. 공식 API 발급이 가능한 플랫폼

### 2-1. 1순위 — 지금 바로 쓸 수 있는 것

| 플랫폼 | 얻는 데이터 | 발급 | 한도 | 비용 | 비고 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| **네이버 검색 오픈API** | 블로그, 카페글, 지식iN, 뉴스, 웹문서, 쇼핑 | 개발자센터 앱 등록 | 일 25,000회 | 무료 | 한국어 커버리지 최고. 유레카에 가장 중요 |
| **YouTube Data API v3** | 영상 댓글, 영상 메타데이터 | Google Cloud 프로젝트 | 일 10,000 units | 무료 | `commentThreads.list` 1 unit, `search.list` 100 units — 검색은 아끼고 댓글을 많이 파는 설계가 유리 |
| **App Store 고객 리뷰 RSS** | 앱 리뷰 (경쟁 앱 포함) | 불필요 | 명시 없음 | 무료 | 공개 RSS라 자사 앱 제한이 없음. B로 가기 전 먼저 검토 |
| **빅카인즈 (한국언론진흥재단)** | 100여 개 언론사 뉴스 | 신청 | 확인 필요 | 무료 | 이용 조건·상업적 활용 범위 **확인 필요** |
| **공공데이터포털 (data.go.kr)** | 민원·소비자 상담 등 | 활용 신청 | API별 상이 | 무료 | "실제 불편"이라는 성격에 잘 맞는 후보. 어떤 데이터셋이 쓸 만한지 **조사 필요** |

### 2-2. 2순위 — API는 있으나 비용·승인 장벽이 큰 것

| 플랫폼 | 얻는 데이터 | 발급 | 한도 | 비용 | 비고 |
| :-- | :-- | :-- | :-- | :-- | :-- |
| **Reddit Data API** | 서브레딧 게시글·댓글 | 수동 승인 (Responsible Builder Policy, 2026-06-05 개정) | 무료: OAuth 100 QPM | 무료 티어는 **비상업 전용**, 상업 $0.24/1k calls | 승인 2~4주, 거절 가능. 날짜 범위 검색·댓글 검색 불가, 리스팅 1,000건 상한 |
| **X (Twitter) API** | 포스트 | 즉시 (pay-per-use) | 읽기 월 200만 건 상한 | **신규 무료 티어 없음**. 읽기 $0.005/post | 2026-02-06부터 pay-per-use가 기본. 기존 Basic/Pro는 신규 가입 불가 |
| **App Store Connect API** | 자사 앱 리뷰 | Apple 개발자 계정 | 시간당 약 50회 | 무료 | **자사 앱만** — 경쟁 앱 불가. 유레카 용도로는 부적합 |
| **Google Play Developer API** | 자사 앱 리뷰 | Google Play 콘솔 | — | 무료 | **자사 앱, 최근 7일만** — 유레카 용도로는 부적합 |

> **Reddit·X 판단**: 영어권 데이터라 한국 메이커 대상 문제 발굴에 우선순위가 낮고, 비용·승인 리스크가 크다.
> MVP에서는 **보류**하고, 해외 확장 시점에 다시 검토하는 것을 제안한다.

## 3. B. 공식 API가 없어 크롤링을 검토해야 하는 플랫폼

크롤링은 법적 위험이 실재한다(5절 참고). 아래 위험도는 **접근 제약과 약관** 기준이다.

### 3-1. 검토 가능 — robots.txt 준수 시

| 플랫폼 | 얻는 데이터 | 위험도 | 비고 |
| :-- | :-- | :-- | :-- |
| **디시인사이드** | 갤러리 게시글·댓글 | 중 | 공개 게시판. 노이즈·비속어 비율 높아 정제 비용 큼 |
| **클리앙 / 뽐뿌 / 루리웹 / 에펨코리아** | 자유게시판·질문글 | 중 | 공개 게시판. 생활·소비 관련 불편이 잘 드러남 |
| **OKKY / 인프런 질문 게시판** | 개발자 질문·고충 | 중 | 생산성/업무 카테고리와 직결 |
| **벨로그 / 티스토리** | 개인 기술 블로그 회고 | 중 | RSS 제공 블로그가 많아 부담이 적음 |
| **Google Play 리뷰** | 앱 리뷰 (경쟁 앱 포함) | 중 | 공식 API가 자사·7일 제한이라 대안이 필요. 오픈소스 라이브러리·상용 스크래퍼 존재 |

### 3-2. 권장하지 않음 — 로그인·회원제·명시적 금지

| 플랫폼 | 사유 |
| :-- | :-- |
| **블라인드** | 재직자 인증 기반 폐쇄형. 로그인 우회는 정보통신망법 위험 |
| **잡플래닛** | 기업 리뷰 열람에 로그인·기여 요구. 잡코리아 판례와 성격이 유사 |
| **네이버 카페 / 다음 카페 본문** | 카페는 회원제. 검색 API의 스니펫까지만 쓰고 본문 크롤링은 하지 않는다 |
| **쿠팡 등 커머스 리뷰** | 약관상 수집 금지, 봇 차단 강함 |
| **인스타그램 / 당근** | 앱 중심 + 약관상 금지 |

> **원칙: 로그인이 필요한 곳은 크롤링하지 않는다.** 우회 시도 자체가 5절 판례에서 불리하게 작용했다.

---

## 4. 두 방식 비교

| | A. 공식 API | B. 크롤링 |
| :-- | :-- | :-- |
| 안정성 | 스키마 보장, 변경 시 공지 | 마크업 변경에 그대로 깨짐 |
| 법적 위험 | 약관 준수 시 낮음 | 판례 존재, 상시 관리 필요 |
| 커버리지 | 제공 범위로 한정 | 원하는 곳을 넓게 |
| 비용 | 무료~고가 (플랫폼별 편차 큼) | 인프라 + 유지보수 인건비 |
| 착수 속도 | 빠름 (키 발급) | 느림 (사이트별 구현) |

## 5. 크롤링 시 반드시 지킬 것

국내에 **대법원 판례**가 있다. 잡코리아 채용정보를 사람인이 크롤링해 자사 서비스에 사용한 사건에서
법원은 **데이터베이스권 침해 및 부정경쟁행위**로 판단해 369건에 대해 건당 50만 원, 총 1억 9,800만 원 배상을 명했다.

판결에서 불리하게 작용한 요소가 그대로 우리의 준수 사항이 된다.

| 판례에서 문제가 된 행위 | 우리가 지킬 것 |
| :-- | :-- |
| robots.txt를 확인조차 하지 않음 | **robots.txt를 읽고 준수한다** |
| IP 차단을 VPN으로 우회 | **차단되면 중단한다. 우회하지 않는다** |
| 정체를 숨기고 접근 | **User-Agent에 서비스명·연락처를 명시한다** |
| 무차별 복제 후 출처 삭제 | **요약 중심으로 저장하고 출처를 반드시 표시한다** |

추가로 지킬 것:

- **요청 간 지연**을 두어 상대 서버에 부담을 주지 않는다.
- **원문 전량 저장 금지.** PRD F03 정책과 동일하게 요약을 기본으로 하고, 허용된 경우에만 짧은 발췌와 원문 링크를 남긴다.
- **개인정보를 수집·저장하지 않는다.** 작성자 ID·닉네임은 저장 대상에서 제외한다.
- 수집 시각·출처 URL·라이선스 상태를 **레코드마다 함께 기록**한다.

## 6. MVP 1차 조합 제안

PRD의 초기 카테고리(생산성/업무, 커리어/자기계발, 라이프스타일)를 덮는 최소 조합이다.

| 순서 | 소스 | 방식 | 이유 |
| :-- | :-- | :-- | :-- |
| 1 | 네이버 검색 API (카페글·지식iN·블로그) | A | 한국어 불편 데이터의 폭이 가장 넓다. 무료·즉시 |
| 2 | YouTube 댓글 API | A | 제품·서비스 사용 후기가 구체적으로 드러난다 |
| 3 | App Store 리뷰 RSS | A | 앱 사용 중 겪는 불편이 명확한 문장으로 남는다 |
| 4 | 개발자·직장인 커뮤니티 (OKKY, 클리앙 등) | B | 생산성/업무 카테고리를 채우려면 필요 |

**1~3만으로 먼저 파이프라인을 완성하고**, 데이터가 부족한 카테고리에 한해 4를 추가하는 순서를 제안한다.
크롤링을 나중으로 미루면 법적 검토 시간을 벌 수 있고, 초기 구현 속도도 빨라진다.

| 수집 주기 | 실시간 / 일 배치 / 수동 중 무엇으로 시작할지 |
| 최소 근거 기준 | 몇 건 이상 모여야 하나의 "문제"로 묶을지 (PRD 9절) |
| 저장 정책 | 요약만 저장할지, 원문 해시를 함께 둘지 (중복 판정용) |
