# 아이디어 생성 팀원에게 — IA·프롬프트 3종 생성 규칙

**작성: 박민규** · 대상: 트렌드 키워드 → 아이디어 생성을 맡는 팀원 (④)
**소비처**: `Final/Frontend/v1-trend-incubator.html`의 `renderIAFlow()` / 프롬프트 결과 화면 (사양은 [IDEA_DETAIL_SPEC.md](IDEA_DETAIL_SPEC.md))
**축 정의(플랫폼×유형 9조합이 무엇을 바꾸는지)**: [아이디어_생성_설계.md](아이디어_생성_설계.md)

> **구현 완료 (v1)**: 아래 두 규칙은 `Final/Backend/app/agents/idea_agent.py` +
> `app/ideas/`에 구현되어 `POST /api/trends/{keyword_id}/ideas`로 나갑니다.
> 개수는 3개로 고정했습니다(문서 원안 5개 대신 — 현재 프론트 UI·목업과 맞춤).

## 왜 이 문서가 필요한가

지금 만드는 아이디어 상세 화면(가로형 IA + 1일·일주일·한달 프롬프트 3종)은 프론트에서 목업 데이터로 완성해뒀습니다. 실제 생성이 붙으려면 아이디어 생성 쪽에서 **이 문서의 두 규칙**을 지켜서 값을 채워주면 됩니다. 프론트 코드는 손댈 필요 없습니다.

먼저 참고: `Final/Backend/app/schemas/models.py`의 현재 `Idea`는 v0(문제→아이디어) 스키마라서 `problem_id`·`why_linked`·`fit_reason`처럼 지금 방향과 안 맞는 필드고, `ia`·`mvpFeatures`·`stack` 같은 새 필드가 없습니다. v1용으로 새로 정의가 필요합니다 — 그건 이 아이디어 생성 로직을 맡는 쪽 소관이라 여기선 건드리지 않았습니다. 아래 스키마를 참고해서 정하시면 됩니다.

## 아이디어 하나가 가져야 할 필드

```
shortName, slogan, target, problem, solution, diff,
mvpFeatures: string[], futureFeatures: string[], stack, architecture,
ia: (아래 1번 규칙)
```

이 중 `ia`를 만드는 규칙과, 이 필드들 전체로 프롬프트 3종을 만드는 규칙이 아래 두 개입니다.

---

## 규칙 1 — IA(`ia`) 생성 지침 (가로형 렌더 전제)

프론트가 `ia`를 **왼쪽(서비스) → 오른쪽(2Depth)**으로 그립니다. 세로 나열이 아니라 실제 화면 폭에 카드가 나란히 배치되는 구조라서, 아래 크기 가이드를 지켜야 화면이 깨지지 않습니다.

```
ia: Array<{
  depth1: string,               // 1Depth 화면/섹션명
  depth2: Array<{ title: string, desc: string }>
}>
```

이 규칙 블록은 아이디어 생성 프롬프트 안에 그대로 끼워 넣으시면 됩니다:

```
## 서비스 정보구조(IA) 작성 규칙

아이디어마다 서비스의 화면 구조를 depth1(화면·섹션) → depth2(그 안의 기능)
2단 트리로 작성하라. 이 트리는 가로로 나란히 그려지므로 아래 크기를 지켜라.

- depth1은 2~4개로 하라. 5개를 넘기지 마라 — 가로 폭을 벗어난다.
- depth1 이름은 명사형으로 10자 내외. 예: "메인 홈 (지도 & 레이더)"
- 각 depth1 아래 depth2는 1~3개로 하라.
- 서로 다른 depth1끼리 depth2 개수 차이를 2개 이상 벌리지 마라
  (하나는 1개, 다른 하나는 4개처럼 극단적으로 불균형하면 화면에서
  카드 높이가 비대칭으로 어색해진다).
- depth2의 title은 8자 내외 기능명, desc는 30자 내외 한 문장으로
  "무엇을 보여주는지/무엇을 하는지"만 적어라. 근거 없는 수치를
  넣지 마라 (예: "월 10만명이 이용" 금지).
- depth1의 나열 순서는 사용자가 실제로 마주치는 순서(온보딩 → 핵심
  기능 → 저장/공유)로 하라. 이 순서가 그대로 왼쪽에서 오른쪽 방향의
  플로우로 그려진다.
```

## 규칙 2 — 기간별 프롬프트 3종 생성 메타 프롬프트

**중요한 설계 결정 — 반드시 지켜야 함:** 1일·일주일·한달은 **하나의 프로젝트가 시간 순서로 진행되는 로드맵이 아닙니다.** 예전에 있던 `구현 난이도`(초급·중급·도전)를 그대로 기간 이름으로 바꿔 부른 것뿐이고, 세 프롬프트는 **서로 독립된 완성본**입니다. 차이는 일정이 아니라 **완성도·요구 스킬**입니다. 처음 이 프롬프트를 만들 때 "일주일 = Day1~5 로드맵", "한달 = 1주차~4주차 마일스톤"으로 짰다가, 그게 세 프롬프트를 한 프로젝트의 진행 단계처럼 보이게 만든다는 지적을 받고 걷어냈습니다. **"Day 1", "1주차" 같은 시간 진행 표현은 프롬프트 출력에 절대 넣지 마세요.**

| | 1일 | 일주일 | 한달 |
|---|---|---|---|
| AI 행동 | 질문 없이 즉시 전체 코드 | **먼저 질문 → 답 받고 착수** | 아키텍처 설계 → 검토 후 구현 |
| IA 반영 범위 | 1Depth 핵심 1~2개만 | 1·2Depth 전체 | 1·2Depth 전체 + 확장 기능 |
| 데이터 | 인라인 목업 + localStorage | 경량 BaaS, 실제 저장·조회 | DB 스키마·인증·배포·테스트 |
| 요구 스킬 | 그대로 실행만 하면 됨 | BaaS 연동 이해 | 프론트·백엔드·배포 전반 |

아래는 이 표를 실제로 만족하는 프롬프트 3종을 생성하는 메타 프롬프트입니다. `common_prompts.with_rules()`로 감싸서 쓰세요. 플레이스홀더 치환은 프로젝트 컨벤션대로 `str.replace()`로 하세요 — 프롬프트 안에 JSON 예시 중괄호가 있어서 `str.format()`을 쓰면 깨집니다.

```
## 바이브코딩 프롬프트 3종 생성

아래 아이디어 정보를 바탕으로, Cursor/Claude 같은 AI 코딩 도구에
그대로 붙여넣을 수 있는 완성된 프롬프트를 "1일"·"일주일"·"한달"
세 가지 만들어라. 이 셋은 같은 프로젝트의 진행 단계가 아니라
서로 다른 완성도의 독립된 결과물이다.

[아이디어 정보]
- 서비스명: {shortName}
- 한 줄 컨셉: {slogan}
- 타깃: {target}
- 해결하는 문제: {problem}
- 해결 방식: {solution}
- 차별점: {diff}
- MVP 핵심 기능: {mvpFeatures}
- 확장 기능: {futureFeatures}
- 추천 기술 스택: {stack}
- 전체 아키텍처: {architecture}
- 서비스 정보구조(IA): {ia_outline}
- 플랫폼: {platform} / 기획 유형: {type} / AI 활용 수준: {ai}

[공통 형식 — 세 프롬프트 모두]
"당신은 뛰어난 풀스택 시니어 소프트웨어 엔지니어입니다"로 시작해
프로젝트 목표(서비스명·컨셉·타깃·문제·해결방식·차별점)와
시스템 아키텍처·IA를 그대로 담아라. IA는 위에 주어진 것을 그대로
쓰고, 절대 임의로 다른 화면 구성(예: "메인 랜딩/핵심 기능/공유"
같은 일반적인 4페이지 구조)을 지어내지 마라 — 아이디어마다 실제
IA가 달라야 한다.

[1일 프롬프트]
- 질문하지 말고 즉시 전체 코드를 작성하라고 지시하라.
- IA의 1Depth 중 핵심 1~2개에만 집중하고 나머지는 최소화하라고 하라.
- 프론트엔드 단독, 목업 데이터 + localStorage로 제한하라.
- 회원가입·결제·백엔드 서버는 배제하라고 명시하라.

[일주일 프롬프트]
- 바로 코드를 쓰지 말고 아래 네 가지를 먼저 사용자에게 물어본
  뒤 답을 받고 시작하라고 지시하라: (1) 타깃 설명이 실제 사용
  상황과 맞는지 (2) IA 중 가장 먼저 완성하고 싶은 화면 (3) 데이터
  출처(직접 입력/공개 API/목업 중 선택) (4) 디자인 톤 유지 여부.
- IA를 1·2Depth 전체 반영하고, 목업이 아니라 실제 데이터베이스에
  저장·조회되는 인증·데이터 흐름(경량 BaaS)을 갖추라고 하라.
  이것이 1일 버전과의 핵심 차이임을 프롬프트 안에 명시하라.
- 결제·복잡한 권한 체계는 제외하라고 하라.
- "Day 1", "1주차" 같은 일정 표현을 쓰지 마라.

[한달 프롬프트]
- 먼저 전체 아키텍처(화면 구조·데이터 모델·API·인증)를 설계해
  검토받은 뒤 구현하라고 지시하라.
- IA와 확장 기능을 전부 반영하고, 인증·실 데이터베이스·배포
  파이프라인·테스트를 갖춘 프로덕션 수준으로 만들라고 하라.
  1일·일주일 버전과의 차이가 일정이 아니라 완성도임을 프롬프트
  안에 명시하라.
- 프론트엔드뿐 아니라 백엔드·배포까지 다루는 실력이 필요한
  범위임을 명시하라.
- 각 구조적 결정의 이유를 남기라고 하라(ADR 형식).
- "1주차", "2주차" 같은 일정 표현을 쓰지 마라.

[출력 형식]
아래 JSON 하나만 출력하라. 다른 텍스트를 앞뒤에 붙이지 마라.
{
  "1일": "...(완성된 프롬프트 전문)...",
  "일주일": "...(완성된 프롬프트 전문)...",
  "한달": "...(완성된 프롬프트 전문)..."
}
```

`{ia_outline}`은 `ia` 배열을 아래처럼 텍스트로 펼친 것을 넣으세요(프론트의 `formatIAOutline()`과 같은 모양):

```
- 메인 홈 (지도 & 레이더)
  · 위치 기반 지도/목록 뷰 — 반경 5km 내 스팟 핀 표시 및 실시간 거리 계산
  · 퀵 필터 & 검색 — '오늘 재고 있음' 토글 및 키워드 검색
- 스팟 상세 & 검증 리뷰
  · ...
```

## 실제 구현과의 관계 (v1, 갱신됨)

이 절은 원래 "프론트 임시 구현"을 설명했지만 실제 구현 후 갱신합니다.

- **규칙 1(IA)** 은 `app/prompts/idea_prompts.py`의 `build_idea_prompt()`가 이
  블록을 그대로 프롬프트에 넣고, LLM이 만든 아이디어마다 `ia` 필드로 나옵니다.
  플랫폼별 depth1 개수 제약(`ia_shape`)은 `app/ideas/axes.py`에 있습니다.
- **규칙 2(프롬프트 3종)** 는 **LLM을 다시 부르지 않습니다.** 프론트
  `v1-trend-incubator.html:buildPromptForPeriod()`(예전 `buildPrompts()`에서
  이름이 바뀌었습니다)가 이미 이 문서 규칙(시간 진행 표현 금지 등)을 만족하는
  검증된 결정적 템플릿이라, `app/prompts/idea_prompts.py`의
  `build_period_prompt()`로 그대로 파이썬 이식했습니다. 응답에 `prompts.day`
  /`prompts.week`/`prompts.month`가 전부 담겨 나가므로, 프론트에서 기간 칩을
  바꿔도 재요청이 필요 없습니다.
- **주의**: 화면 기간 칩 라벨(`하루`/`일주일`/`한 달 이상`)과 이 문서의 표기
  (`1일`/`일주일`/`한달`)가 다릅니다 — 내부 키는 `day`/`week`/`month`로
  통일했고 양쪽 표기를 전부 별칭으로 받습니다. 자세한 표는
  [아이디어_생성_설계.md](아이디어_생성_설계.md) 0절 참고.
- 두 규칙 다 프론트 렌더 코드(`renderIAFlow`, `showIdeaDetail`)는 그대로
  두었고, "추천 AI 툴" 섹션만 하드코딩 pill 2개를 `idea.aiTools[]` 바인딩으로
  바꿨습니다(화이트리스트 카탈로그 — 4절 참고).
