# Gemini 실데이터 파일럿 — 2026-09-13

실제 검색 → Gemini 판별 → 묶기 → 근거 조립 경로를 실행했다. 연결은 동작하지만 게시 가능한 문제는 아직 없다. 가이드·홍보 글을 실제 사용자 불편으로 오인하는 문제를 발견해 프롬프트를 보강했다. 동일 표본에서 오탐 의심 사례가 줄었으나, 잘린 스니펫을 추론하는 문제는 남았다.

## 실행 범위

- 모델: `gemini-3.5-flash-lite`, 실제 호출 모드. `.env`의 기본 모의 실행 설정은 유지.
- 카테고리: IT/생산성. 사전 첫 키워드 `회의록` × 불편 표현 10개.
- 소스 옵션: 블로그. 내부적으로 네이버 블로그·다음 블로그·다음 웹문서 검색.
- 검색어별 반환 상한 5건, 페이지 상한 1. 전체 저장 상한 50건, 판별 상한 50건.
- 검색 결과의 스니펫만 사용. 원문 페이지는 열지 않았고 화면 게시도 하지 않았다.
- 하네스 팀: 실행·프롬프트 보강 담당과 독립적인 코드·표본 검토 담당으로 분리했다. 품질 평가는 AI 정성 검토이며 사람의 정답 라벨이 아니다.

```bash
cd Final/Backend
LLM_DRY_RUN=false LLM_MAX_RETRIES=0 LLM_TIMEOUT_SEC=45 \
COLLECT_MAX_PAGES=1 COLLECT_PER_QUERY_LIMIT=5 MAX_LLM_ITEMS=50 \
.venv/bin/python scripts/run_collect_only.py \
  --category 'IT/생산성' --sources 블로그 --keywords 1 --limit 50 --yes
```

위는 이미 실행한 명령의 기록이다. 비교 평가를 위해 다시 수집할 필요는 없다. `--limit`만으로는 저장량을 제한하지 않으므로 검색어 수와 `COLLECT_PER_QUERY_LIMIT`를 함께 제한했다. 스크립트의 예상 검색 호출 수는 내부 엔드포인트 수·재시도를 포함하지 않으며 실제 HTTP 요청 수로 해석하면 안 된다.

원문 출처는 네이버 블로그 15건, 다음 블로그 18건, 다음 웹문서 13건이다. 규칙 탈락 20건의 사유는 모두 불편 신호 없음이다. 이 세 검색 경로가 서로 독립적인 원문 출처 세 곳임을 보장하지는 않는다.

기존 판별은 오류 강등 경고 없이 완료됐다. 보강 후에는 실제 HTTP 4회가 모두 200이었고, 응답 사용량 합계는 22,143토큰이다. 이 토큰 수에는 최초 판별·이전 연결 확인 호출이 포함되지 않는다.

기존 판별 결과는 단독 묶음 12개, 보강 후 첫 판별 결과는 단독 묶음 2개였다. 최소 묶음 5건에 미달해 모두 승격 대기이며, 승격 후보와 근거 묶음은 0개다. 근거 조립기의 빈 입력 경로까지 정상 실행했다. 실제 자료가 채워진 근거 묶음의 품질은 아직 검증하지 못했다. 묶기 임계값과 게시 기준을 낮추지 않았다.

## 품질 검토와 변경

기존 양성 12건 중 8건은 가이드·상품 권유의 일반론이나 가정 질문을 글쓴이의 경험으로 인정한 오탐 의심 사례였다. 나머지는 직접 경험이 분명한 1건과 판단이 모호한 3건이었다.

`Final/Backend/app/prompts/interpreter_prompts.py`에 실제 경험과 안내용 예시를 구분하는 절차, 독자 대상 질문·마케팅 후기 처리, 잘린 스니펫을 상상하지 않는 규칙과 일반적인 예시를 추가했다. 특정 수집 ID나 서비스명을 예외 목록으로 넣지는 않았다.

보강 후 두 실행에서 지적한 8건 모두 불편 아님으로 바뀌었다. 남은 양성은 다음과 같다.

강도 비교 26건에는 음성의 null 24건이 포함된다. 나이·성별은 모두 null로 일치했으므로 양성 추출 능력을 검증한 것은 아니다. 지불 신호도 모두 false이며 규칙으로 계산하므로 Gemini 재현성 지표가 아니다. 제목의 대상 독자를 글쓴이 역할로 잘못 추정하는 사례가 반복 평가에서 1건 관측됐다.

같은 표본을 보고 프롬프트를 수정했으므로 이 결과는 별도 평가 표본에 대한 정확도가 아니다. 단일 키워드·블로그 중심의 작은 표본이며, 사람의 정답 검토와 새로운 표본 평가가 필요하다.

## 저장과 이어서 할 일

- 원본 수집·최초 판정: `Final/Backend/data/corpus/`. 최초 판정에는 위 오탐 의심 사례가 남아 있으므로 검증된 데이터로 사용하지 않는다.
- 비교 자료: `Final/Backend/data/pilots/2026-09-13-gemini/`. `baseline.json`, 프롬프트 두 버전, `revised-1.json`, `revised-2.json`, `consistency.json`, `evidence.json`, `revised-manifest.json`을 저장했다.
- 보강 후 첫 결과로 재구성한 코퍼스: 같은 평가 폴더의 `revised-corpus/`. 원본에 새 판정을 append하지 않아 최초·수정 판정이 섞이지 않는다. 이 자료도 남은 보류 사례를 검토하기 전에는 게시용으로 쓰지 않는다.
- 평가 스크립트 `evaluate.py`는 저장된 판정 체크포인트가 있으면 API 재호출 없이 재사용한다. 코퍼스와 평가 자료는 기존 정책대로 Git에서 제외된다.
- 검증: `test_judge_pains.py`, `test_interpreter_agent.py`, `test_gemini_llm.py`, `test_no_numbers.py` 총 150개 통과. 이는 회귀 테스트이며 실데이터 정확도 측정과 별개다.

다음 우선순위는 커뮤니티·질문형 글의 새 표본에서 실제 경험의 비율을 확인하고, 남은 보류 사례와 역할 추정을 검토하는 것이다. 기존 판정 저장소는 같은 ID 재판정의 첫 값을 읽는 경로가 있으므로 재판정 버전 선택을 정리한 뒤 정식 코퍼스로 통합해야 한다. 이후 실제 후보가 충분히 생기면 근거 집계를 검증하고 ③ 문제정의 생성기와 화면 연결을 진행한다.
