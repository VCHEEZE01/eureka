## 0. 한눈에 보기

식당으로 비유하면 이렇다.

- **백엔드 = 주방.** 재료를 사 오고(수집), 손질하고(계산), 요리한다(분류·AI 글쓰기). 손님이 올 때마다 장을 보러 가지 않고, 매일 아침 미리 준비해 둔다.
- **프론트엔드 = 홀.** 주방이 내준 음식을 예쁘게 담아서 보여준다. 홀에서 요리를 새로 만들지는 않는다.
- **스키마 = 주문서 양식과 접시 크기.** 주방과 홀이 같은 양식을 써야 음식이 제대로 나간다.
- **더미 데이터 = 모형 음식.** 모형도 진짜 접시 크기에 맞춰 만들어야, 나중에 진짜 음식으로 바꿔 담기만 하면 된다.

그래서 순서는 **스키마와 규칙 정하기 → 그 모양대로 더미 72개 만들기 → 화면 연결 → 나중에 진짜 수집 붙이기**다.

예전 유레카(문제정의 서비스)와 가장 크게 다른 점은 **실행 시점**이다. 예전에는 사용자가 입력할 때마다 수집·분석을 새로 돌렸다. 새 서비스는 사용자가 입력하는 것이 없고 모두가 같은 키워드 목록을 본다. 그래서 **하루 한 번 미리 계산해 두고, 화면은 준비된 결과를 읽기만** 한다.

## 1. 누가 무엇을 하나

**백엔드가 하는 일**

1. 후보 키워드 모으기
2. 네이버·유튜브·스레드에서 숫자 모으기
3. 숫자 계산하기(월간 검색량, 변화율, 플랫폼 비중, 6개월 추이)
4. 트렌드 탭 / 급상승 탭 / 상태 딱지 나누기
5. AI로 설명 글 쓰기
6. 저장하고 API로 내주기

**프론트엔드가 하는 일**

1. API가 준 목록과 리포트 보여주기
2. 숫자 모양 꾸미기(`58000` → `58,000`, `420.0` → `+420%`)
3. 받은 목록 안에서 검색·분야 필터·정렬하기
4. 도넛과 그래프 그리기
5. 보관함(브라우저에 저장, 로그인 없음)

**꼭 지킬 규칙 네 가지**

1. **숫자는 AI가 만들지 않는다.** 검색량, 언급량, 변화율, 비중, 그래프 값은 전부 수집한 값을 코드로 계산한다. AI는 글만 쓴다. (예전 유레카의 가장 중요한 규칙을 그대로 가져온다.)
2. **탭, 상태 딱지, 트렌드 강도는 백엔드가 정해진 규칙으로 정한다.** 화면이 숫자를 보고 스스로 분류하지 않는다. 규칙이 바뀌어도 화면은 고칠 필요가 없다.
3. **AI 글은 실제로 모은 글·영상 안에서만 쓴다.** 어떤 근거 글을 봤는지 id를 함께 남긴다.
4. **모든 응답에 기준일과 더미 여부를 붙인다.** 사용자가 "언제 기준 숫자인지", "진짜인지 예시인지" 알 수 있게 한다.

**하루 한 번 미리 만드는 이유**

- 키워드 72개 × 플랫폼 3곳을 사용자가 들어올 때마다 부르면 화면이 몇십 초씩 멈춘다.
- 유튜브 무료 한도는 하루 10,000단위이고, 검색 한 번에 100단위를 쓴다(하루 약 100번). 요청마다 부르면 금방 바닥난다.
- 밤사이 수집이 실패해도 어제 게시한 결과를 계속 보여줄 수 있다.

"이 키워드로 서비스 아이디어 5개 만들기"는 사용자가 누를 때 실행하는 기능이다. 이 문서의 범위 밖이라 나중에 따로 설계한다.

## 3. 출처별로 실제로 얻을 수 있는 것

> 표시한 조건은 설계 시점 기준이다. **연결하기 전에 반드시 공식 문서와 계정 화면으로 다시 확인한다.** 문서에 없는 요청 방식은 추측해서 만들지 않는다.

**네이버**

- **검색광고 API의 키워드 도구(연관키워드·월간 검색수 조회):** 키워드의 최근 한 달 검색 수(PC+모바일)와 연관 키워드를 준다. 화면의 `월간 검색량`과 `연관어` 후보가 여기서 나온다. 검색광고 계정이 필요하다. **확인 필요:** 계정 발급, 이용 조건, 호출 한도.
- **데이터랩 검색어 트렌드:** 기간별 검색 흐름을 **상대값(가장 높은 날 = 100)**으로 준다. 실제 검색 횟수가 아니다. 6개월 그래프 모양과 전주 대비 변화율 계산에 쓰고, 실제 숫자 크기는 위 검색광고 월간 검색수로 맞춘다. 요청 한 번에 비교할 수 있는 검색어 묶음 수에 제한이 있다. **확인 필요:** NAVER API HUB에서의 요청 주소와 한도.
- **블로그·카페 검색(기존 Backend에 이미 연결됨):** 최근 글의 제목, 요약, 링크를 준다. AI 글의 근거로 쓴다. 기간 필터가 없어서 날짜순으로 받아 최근 30일만 거른다.

**유튜브**

- **영상 검색(`search.list`, 날짜 범위 지정 가능):** 기간 안에 올라온 관련 영상 수와 목록을 준다. `월간 언급량`의 유튜브 부분과 근거 영상이 여기서 나온다. 한 번에 100단위를 쓰므로 키워드마다 매일 부르지 않고 나눠서 부른다.
- **댓글(`commentThreads`):** 반응 근거로 쓴다. 기존 Backend에 연결 코드가 있다.
- **인기 영상(`videos.list`, 한국 인기 차트):** 제목에서 새 후보 키워드를 뽑는 데 쓴다.
- **확인 필요:** API로 받은 데이터를 AI 분석에 쓰는 것이 이용 정책에 맞는지(기존 `Backend/FREE_SOURCE_SETUP.md`에 적어 둔 주의 사항).

**스레드**

- **키워드 검색(`threads_keyword_search` 권한):** 관련 공개 게시글을 준다. `월간 언급량`의 스레드 부분과 근거 글이 여기서 나온다. Meta 앱 권한 승인이 필요하다. **확인 필요:** 승인 여부, 기간 조건, 한국어 결과 양.

**후보 키워드는 어떻게 찾나**

"요즘 뜨는 것"을 인터넷 전체에서 완전 자동으로 찾아내는 일은 크고 어렵다. 그래서 MVP는 이렇게 시작한다.

1. 운영자가 후보 목록을 관리한다(처음에는 사람이 기사와 SNS를 보고 넣는다).
2. 유튜브 인기 영상 제목에서 AI가 후보 단어를 뽑는다.
3. 사람이 승인한 후보만 숫자 수집 대상이 된다.

## 4. 계산 규칙 — 코드가 한다

플랫폼마다 숫자의 단위가 다르다. 네이버는 "검색한 횟수", 유튜브·스레드는 "올라온 게시물 수"다. 그래서 그냥 더하거나 비교하지 않고 아래처럼 정한다.

```python
# 모든 계산의 기준일(base_date)은 스냅샷을 만든 날이다. 예: 2026-09-15

# ① 월간 검색량: 네이버 검색광고의 최근 30일 검색수(PC+모바일)
monthly_search_volume = naver_monthly_pc + naver_monthly_mobile

# ② 월간 언급량: 최근 30일 동안 올라온 관련 유튜브 영상 수 + 스레드 게시글 수
monthly_mention_volume = youtube_posts_30d + threads_posts_30d

# ③ 플랫폼 비중: "이 키워드가 평소보다 어느 플랫폼에서 더 화제인가"
#    단위가 달라서, 각 플랫폼 값을 "추적 중인 전체 키워드의 중간값"으로 나눠 같은 척도로 맞춘다.
#    예) 네이버 58,000 / 네이버 중간값 100,000 = 0.58배
relative = {p: value_30d[p] / median_of_all_keywords[p] for p in ("naver", "youtube", "threads")}
platform_share = {p: round(relative[p] / sum(relative.values()) * 100) for p in relative}
# 반올림 때문에 합이 99나 101이 되면, 가장 큰 칸에서 차이를 더하거나 빼서 딱 100으로 맞춘다.

# ④ 전주 대비 변화율: 플랫폼별 "최근 7일 ÷ 그 전 7일" 변화를 비중만큼 섞는다.
rate = {p: (last_7d[p] - prev_7d[p]) / prev_7d[p] * 100 for p in platforms if prev_7d[p] > 0}
weekly_change_rate = sum(platform_share[p] / 100 * rate[p] for p in rate)

# ⑤ 6개월 추이(그래프): 최근 6개 달력 월의 월별 합계
#    네이버 = 데이터랩 상대값 흐름을 검색광고 월간 검색수 크기에 맞춰 환산
#    유튜브·스레드 = 그달에 올라온 게시물 수
#    이번 달은 기준일까지의 값을 30일 기준으로 늘려 계산하고, 마지막 값은 ①·②와 같게 맞춘다.

# ⑥ 트렌드 강도: ④의 전주 대비 변화율로 강함 / 보통 / 약함을 정한다 → 바로 아래 "트렌드 강도 규칙"
```

화면의 숫자와 그래프는 반드시 서로 맞아야 한다. 네이버 그래프 마지막 달은 월간 검색량과 같고, 유튜브 마지막 달 + 스레드 마지막 달은 월간 언급량과 같다.

### 트렌드 강도 규칙 — 강함 / 보통 / 약함

트렌드 강도는 **"지난주보다 얼마나 늘었나"** 하나로 정한다. "지난주보다 4배 넘게 늘면 강함, 2배~4배면 보통, 그보다 적으면 약함"이라고 사용자에게 한 줄로 설명할 수 있도록, **몇 배가 됐는지**를 기준으로 끊는다.

| 강도 | 기준 (전주 대비 변화율) | 쉽게 말하면 | 화면 색 |
| --- | --- | --- | --- |
| 강함 (`strong`) | +300% 이상 | 지난주의 4배 이상 | 진한 보라 `#6B42FF` |
| 보통 (`medium`) | +100% 이상 ~ +300% 미만 | 지난주의 2배~4배 | 파랑 `#3B82F6` |
| 약함 (`weak`) | +100% 미만 (0%, 마이너스 포함) | 2배가 안 됨 | 회색 `#94A3B8` |

- **두 탭에 같은 기준을 쓴다.** 탭마다 기준이 다르면 같은 "강함"이 탭에 따라 다른 뜻이 되어 헷갈린다.
- **3단계로 나눈다.** 강함/약함 두 단계로 +150%에서 자르면 급상승 탭 기준과 똑같아진다. 그러면 급상승 탭은 전부 강함, 트렌드 탭은 전부 약함이 되어, 탭 이름을 한 번 더 말하는 것밖에 안 된다.
- **화면 글자는 설정으로 바꿀 수 있다.** 트렌드 탭은 원래 천천히 크는 키워드라 "약함"이 많이 나온다. "인기 키워드인데 약하다고?"라는 오해가 생기면 뜻은 그대로 두고 글자만 "완만"으로 바꾼다.
- 참고로 2026-09-15 기존 더미 36개에 대보면 강함 5개, 보통 16개, 약함 15개로 나뉜다.

```python
SMALL_BASE_POSTS_7D = 200      # 그 전 7일 유튜브+스레드 게시물도 200개 미만이면 "원래 작은 키워드"로 본다

STRENGTH_LABELS = {"strong": "강함", "medium": "보통", "weak": "약함"}   # "약함" → "완만"으로 바꿔도 됨


def trend_strength(k):
    """전주 대비 변화율 하나로 트렌드 강도를 정한다. 두 탭 모두 같은 기준을 쓴다."""

    # ④에서 계산한 전주 대비 변화율.
    # 하루 값끼리가 아니라 "최근 7일 합 ÷ 그 전 7일 합"으로 계산했으므로 하루짜리 반짝에 흔들리지 않는다.
    rate = k.weekly_change_rate

    if rate >= STRENGTH_STRONG_RATE:
        level = "strong"
    elif rate >= STRENGTH_MEDIUM_RATE:
        level = "medium"
    else:
        level = "weak"                 # +100% 미만, 0%, 마이너스는 모두 약함

    # 작은 숫자 착시 막기: 지난주가 원래 아주 작았으면 '강함'까지는 주지 않는다.
    #   예) 지난주 100회 → 이번 주 500회 = +400%지만, 규모가 작아서 '보통'으로 표시
    small_base = (k.prev_7d_naver_search < SMALL_BASE_SEARCH_7D
                  and k.prev_7d_youtube_posts + k.prev_7d_threads_posts < SMALL_BASE_POSTS_7D)
    capped = level == "strong" and small_base
    if capped:
        level = "medium"

    return {"level": level, "label": STRENGTH_LABELS[level], "capped": capped}
```

**새 키워드는 2주 뒤에 게시한다.** 수집을 시작한 첫 주에는 비교할 "그 전 7일" 값이 없어 변화율과 강도를 계산할 수 없다. 그래서 숫자를 모은 지 14일이 지난 키워드만 게시한다.

## 5. 탭과 상태 딱지를 나누는 규칙

노래 차트로 비유하면, **트렌드 키워드는 몇 달째 사랑받는 인기곡**, **급상승 키워드는 이번 달 갑자기 치고 올라온 신곡**이다. 한 키워드는 한 탭에만 들어간다.

```python
# ── 조정 가능한 기준값 (config에 두고 바꿀 수 있게 한다) ──
SURGE_WEEKLY_RATE = 150        # 전주 대비 +150% 이상이면 급상승 후보
SURGE_JUMP_RATIO = 2.0         # 최근 30일이 직전 90일 월평균의 2배 이상이어도 급상승 후보
SURGE_NEW_WITHIN_DAYS = 60     # 처음으로 최소 규모를 넘은 지 60일 이내여야 "새로 뜬 것"
TREND_MIN_MONTHS = 3           # 트렌드는 최근 3개월 연속 최소 규모 이상
TREND_MIN_GROWTH_6M = 20       # 트렌드는 6개월 전보다 +20% 이상
TREND_SCALE_SEARCH = 60000     # 트렌드는 월간 검색량 6만 이상이거나
TREND_SCALE_MENTION = 30000    #          월간 언급량 3만 이상
MIN_SEARCH, MIN_MENTION = 5000, 1000   # 이보다 작으면 어느 탭에도 넣지 않음
VIRAL_DROP_FROM_PEAK = 20      # 최고점 주 대비 최근 7일이 20% 이상 줄면 "일시적 유행"


def classify(k):
    """키워드 하나의 탭과 상태를 정한다. 결과: (tab, status_type) 또는 None(제외)"""

    # 1) 너무 작거나 줄어드는 키워드는 뺀다. (지는 키워드 탭은 없앴다.)
    if k.monthly_search_volume < MIN_SEARCH and k.monthly_mention_volume < MIN_MENTION:
        return None
    if k.growth_6m < 0 and k.weekly_change_rate < 0:
        return None

    # 2) 급상승: 최근에 갑자기 크게 튀었고, 새로 뜬 지 얼마 안 됨
    jumped = k.weekly_change_rate >= SURGE_WEEKLY_RATE or k.jump_ratio >= SURGE_JUMP_RATIO
    is_new = k.days_since_first_over_min <= SURGE_NEW_WITHIN_DAYS
    if jumped and is_new:
        if k.drop_from_peak_week >= VIRAL_DROP_FROM_PEAK:
            return ("surge", "viral")     # 확 떴다가 벌써 식기 시작 → 일시적 유행
        return ("surge", "rising")        # 아직 오르는 중 → 급상승

    # 3) 트렌드: 규모가 크고, 석 달 넘게 꾸준하며, 6개월 동안 늘었음
    big_enough = (k.monthly_search_volume >= TREND_SCALE_SEARCH
                  or k.monthly_mention_volume >= TREND_SCALE_MENTION)
    steady = k.months_over_min_in_a_row >= TREND_MIN_MONTHS
    if big_enough and steady and k.growth_6m >= TREND_MIN_GROWTH_6M:
        return ("trend", "sustained")     # 지속 성장

    # 4) 어느 쪽 기준도 못 넘으면 이번에는 게시하지 않는다(다음 날 다시 계산).
    return None
```

**추가 규칙**

- **졸업:** 급상승이던 키워드가 트렌드 기준을 3개월 연속 넘으면 트렌드 탭으로 옮긴다.
- **애매한 경우:** 숫자 기준이 겹치면 "처음 뜬 지 60일 이내인가"를 먼저 본다. 새로 떴으면 급상승, 오래됐으면 트렌드다.
- **탭 안 순위(`rank`):** 트렌드는 `규모 × 꾸준함` 점수 순, 급상승은 `변화율 × 최근성` 점수 순이다. 화면의 "추천 랭킹순" 정렬이 이 순위를 쓴다.
- **게시 개수:** 탭마다 최대 36개. 넘치면 순위가 낮은 것부터 뺀다. 모자라면 모자란 대로 게시한다(숫자를 채우려고 억지로 넣지 않는다).

## 6. AI 글쓰기 규칙

**AI가 쓰는 칸:** `summary`(한 줄 요약), `why_trending`(왜 뜨는지), `target`(누가 좋아하는지), `sustainability`(얼마나 갈지)

**AI가 쓰지 않는 칸:** 모든 숫자, 탭, 상태, 트렌드 강도, 순위, 플랫폼 비중, 그래프 값

**연관어:** 네이버 검색광고의 연관 키워드에서 가져오고, AI는 그중 관련 없는 것을 빼는 일만 한다.

```text
[AI에게 주는 재료]
- 키워드 이름, 분야
- 계산이 끝난 숫자 (읽기 전용 참고. 글에 숫자를 새로 만들어 넣지 말 것)
- 최근 30일 근거 글·영상 목록 (id, 제목, 요약, 날짜) — 최대 20개

[AI가 돌려줘야 하는 모양 — JSON]
{
  "summary": "...",
  "why_trending": "...",
  "target": "...",
  "sustainability": "...",
  "evidence_ids": ["ev_...", "ev_..."]   ← 실제로 참고한 근거 글 id. 목록에 없는 id는 불합격
}

[금지]
- 근거 글에 없는 사건·수치·기관 이름 지어내기
- 실존 개인(연예인 포함)의 사생활이나 확인되지 않은 이야기
- "무조건", "폭발적으로 100%" 같은 단정 표현
```

**검사와 실패 처리**

- 코드가 결과를 검사한다(칸이 비었는지, 근거 id가 목록에 있는지, 글자 수가 적당한지). 틀리면 한 번만 다시 요청하고, 또 틀리면 그 키워드는 오늘 게시하지 않는다.
- 근거 글이 3개보다 적으면 AI를 부르지 않고 그 키워드를 게시하지 않는다.
- 모델 배치는 기존 Backend의 `LLM_ROUTE_*` 설정 방식(1순위 모델 + 비상용 모델)을 재사용한다.

## 7. API — 화면이 부르는 문

| 요청 | 하는 일 | 쓰는 화면 |
| --- | --- | --- |
| `GET /api/trends?tab=trend` | 트렌드 탭 목록 전체(최대 36개) | 첫 페이지 "트렌드 키워드" 탭 |
| `GET /api/trends?tab=surge` | 급상승 탭 목록 전체(최대 36개) | 첫 페이지 "급상승 키워드" 탭 |
| `GET /api/trends/{keyword_id}` | 키워드 하나의 분석 리포트 | 분석 리포트 화면 |
| `POST /api/trends/{keyword_id}/ideas` | (나중에) 아이디어 5개 만들기 | 아이디어 설정·결과 화면 |

**정해 둔 점**

- **목록은 탭 전체를 한 번에 준다.** 36개 정도라 검색·분야 필터·정렬은 지금처럼 화면이 받은 목록 안에서 한다. 서버에 다시 묻지 않아서 빠르고, new.html 코드를 거의 그대로 쓸 수 있다.
- **목록과 리포트는 같은 스냅샷에서 읽는다.** 카드 숫자와 리포트 숫자가 어긋나지 않는다.
- **오류 모양은 예전 유레카 규칙을 재사용한다:** `{ "error_code": "...", "message": "사용자에게 보여줄 한국어 문장" }`

| error_code | HTTP | 언제 |
| --- | --- | --- |
| `invalid_input` | 400 | `tab` 값이 trend/surge가 아닐 때 |
| `keyword_not_found` | 404 | 없는 키워드 id |
| `snapshot_not_ready` | 503 | 게시된 스냅샷이 하나도 없을 때(첫 설치 직후 등) |
| `internal_error` | 500 | 그 밖의 서버 오류 |

## 8. 스키마 — 주고받는 데이터 모양

API는 파이썬 관례대로 `snake_case` 이름을 쓴다. 화면(new.html)은 받은 뒤 작은 변환 함수로 화면용 이름에 맞춘다(11절).

```python
from datetime import date
from typing import Literal, Optional
from pydantic import BaseModel, Field

# ═══════════════════════ 공통 이름표 ═══════════════════════

# 분야. 화면의 분야 칩 글자와 한 글자도 다르면 필터가 안 된다.
Category = Literal["디저트/푸드", "패션/뷰티", "라이프/취미", "챌린지/놀이", "테크/생산성", "콘텐츠/밈"]

# 데이터를 가져오는 플랫폼 세 곳
Platform = Literal["naver", "youtube", "threads"]

# 어느 탭에 들어가는지. trend = 트렌드 키워드, surge = 급상승 키워드
TabType = Literal["trend", "surge"]

# 상태 딱지. sustained = 지속 성장, rising = 급상승, viral = 일시적 유행
StatusType = Literal["sustained", "rising", "viral"]


# ═══════════════════════ 기준 정보 ═══════════════════════

class SnapshotInfo(BaseModel):
    """이 응답의 숫자가 '언제 만든 결과'인지 알려주는 꼬리표"""
    snapshot_id: str            # 하루 한 번 만든 결과 묶음 이름. 예: "2026-09-15"
    base_date: date             # 숫자를 계산한 기준 날짜. 예: 2026-09-15
    months: list[str]           # 그래프 가로축 달 목록(오래된 달 → 이번 달). 예: ["2026-04", ..., "2026-09"]
    is_dummy: bool              # 더미 데이터면 true. 진짜 수집을 붙이기 전까지는 항상 true
    note: Optional[str] = None  # 화면 아래에 작게 보여줄 안내. 예: "예시 데이터입니다"


# ═══════════════════════ 카드(첫 페이지) ═══════════════════════

class TrendStrength(BaseModel):
    """트렌드 강도. 전주 대비 변화율로 코드가 정한다(4절 '트렌드 강도 규칙')"""
    level: Literal["strong", "medium", "weak"]  # 코드용 값. 화면은 이 값으로 색을 정한다(보라/파랑/회색)
    label: str                                  # 화면에 그대로 보여줄 글자. 예: "강함" / "보통" / "약함"
    capped: bool = False                        # 지난주 규모가 너무 작아 '강함'을 '보통'으로 낮췄으면 true


class KeywordMetrics(BaseModel):
    """카드와 리포트의 숫자 칸 네 개 — 전부 코드가 계산한 값"""
    monthly_search_volume: int = Field(ge=0)   # 최근 30일 네이버 검색 수. 쉼표 없는 숫자(화면이 58,000으로 바꿈)
    monthly_mention_volume: int = Field(ge=0)  # 최근 30일 유튜브 영상 + 스레드 게시글 수
    weekly_change_rate: float                  # 전주 대비 변화율(%). 420.0이면 화면에 "+420%"
    trend_strength: TrendStrength              # 트렌드 강도. +300% 이상 강함 / +100% 이상 보통 / 그 아래 약함


class PlatformShare(BaseModel):
    """도넛 차트와 카드의 플랫폼 태그. 세 값의 합은 반드시 100"""
    naver: int = Field(ge=0, le=100)
    youtube: int = Field(ge=0, le=100)
    threads: int = Field(ge=0, le=100)


class KeywordCard(BaseModel):
    """첫 페이지 카드 한 장에 필요한 것"""
    id: str                     # 키워드 고유 이름표. 탭이 바뀌어도 그대로. 예: "kw_0001"
    rank: int                   # 탭 안 추천 순위(1부터). "추천 랭킹순" 정렬에 사용
    tab: TabType                # 어느 탭에 들어가는지
    name: str                   # 키워드 이름. '#' 없이. 예: "굴비 키링"
    category: Category          # 분야
    summary: str                # 카드의 한 줄 요약(AI가 씀)
    status: str                 # 딱지 글자. 예: "급상승"
    status_type: StatusType     # 딱지 종류(색을 정하는 데 씀)
    metrics: KeywordMetrics
    platform_share: PlatformShare


# ═══════════════════════ 리포트(상세 화면) ═══════════════════════

class PlatformSeries(BaseModel):
    """플랫폼 하나의 6개월 숫자"""
    metric: Literal["search_volume", "mention_count"]  # 네이버 = 검색량, 유튜브·스레드 = 언급 수
    values: list[int]           # SnapshotInfo.months와 같은 순서·같은 길이. 마지막 값 = 이번 달


class PlatformTrend(BaseModel):
    """오른쪽 그래프(네이버/유튜브/스레드 버튼으로 바꿔 보는 것)"""
    naver: PlatformSeries
    youtube: PlatformSeries
    threads: PlatformSeries


class EvidenceItem(BaseModel):
    """AI 글이 참고한 근거 글·영상 한 개"""
    id: str                     # 예: "ev_0001"
    platform: Platform
    title: str
    url: str
    published_at: Optional[date] = None   # 날짜를 모르면 비워 둠(지어내지 않음)
    snippet: str = ""                     # 짧은 요약 또는 발췌


class ReportAnalysis(BaseModel):
    """보라색 설명 상자의 세 칸(AI가 씀)"""
    why_trending: str           # 왜 지금 뜨고 있는가
    target: str                 # 핵심 타깃 및 소비자 반응
    sustainability: str         # 트렌드 지속성 전망
    evidence_ids: list[str]     # 이 글을 쓸 때 참고한 근거 id. 더미에서는 빈 목록


class KeywordReport(KeywordCard):
    """분석 리포트 = 카드 내용 전부 + 아래 칸들"""
    analysis: ReportAnalysis
    related_keywords: list[str] = Field(min_length=1, max_length=5)  # 연관어(보통 5개, '#' 없이)
    platform_trend: PlatformTrend
    evidence: list[EvidenceItem] = []     # 근거 목록. 더미에서는 빈 목록
    limitations: list[str] = []           # 숫자의 한계 안내. 예: "언급량은 수집한 게시물 수이며 전체 인터넷 수가 아닙니다"


# ═══════════════════════ API 응답 ═══════════════════════

class TrendListResponse(BaseModel):
    """GET /api/trends?tab=... 의 응답"""
    snapshot: SnapshotInfo
    tab: TabType
    criteria: str               # 이 탭을 고른 기준 한 줄. 예: "최근 60일 안에 새로 떠서 전주 대비 +150% 이상 오른 키워드"
    items: list[KeywordCard]    # rank 순서로 정렬된 카드 목록(최대 36개)


class KeywordReportResponse(BaseModel):
    """GET /api/trends/{keyword_id} 의 응답"""
    snapshot: SnapshotInfo
    report: KeywordReport


class ErrorResponse(BaseModel):
    """모든 오류의 공통 모양"""
    error_code: Literal["invalid_input", "keyword_not_found", "snapshot_not_ready", "internal_error"]
    message: str                # 사용자에게 그대로 보여줄 수 있는 한국어 문장(비밀값·오류 원문 금지)
```

### 응답 예시 — 리포트 하나 (더미)

## 9. 저장 구조 — DB 표

MVP는 기존 설정(`DATABASE_URL=sqlite:///./eureka.db`)대로 SQLite 파일 하나로 시작한다.

```text
keyword_candidates   후보 키워드 목록 (사람이 넣거나 유튜브 인기 영상에서 뽑음)
  - id, name, category, source("manual"|"youtube_popular"), approved(bool), created_at

keywords             승인된 키워드 (id는 한 번 정하면 바뀌지 않음)
  - id("kw_0001"), name, category, first_seen_date, created_at

metric_points        날짜별로 모은 숫자 — 모든 계산의 원재료
  - keyword_id, platform, metric("search_count"|"search_index"|"post_count"),
    date, value, source, collected_at
  - 같은 (keyword_id, platform, metric, date)는 한 줄만 (다시 수집하면 덮어씀)

evidence_items       근거 글·영상
  - id("ev_0001"), keyword_id, platform, title, url, published_at, snippet, collected_at

snapshots            하루 한 번 만든 결과 묶음
  - snapshot_id("2026-09-15"), base_date, status("draft"|"published"|"failed"), is_dummy, created_at

snapshot_keywords    스냅샷 안의 키워드별 계산·분류·AI 글 결과 (화면에 나가는 모양 그대로)
  - snapshot_id, keyword_id, tab, rank, status_type,
    metrics_json, platform_share_json, platform_trend_json,
    summary, why_trending, target, sustainability, related_keywords_json, evidence_ids_json,
    llm_model, prompt_version
```

- API는 `status = "published"`인 가장 최근 스냅샷만 읽는다. 오늘 배치가 실패하면 어제 게시본이 그대로 보인다.
- 계산 결과를 `snapshot_keywords`에 통째로 저장해 두어서, 목록·리포트 API는 계산 없이 읽기만 하면 된다.

## 10. 폴더 구조 — 구현을 시작할 때

지금은 기존 `Backend/` 폴더를 건드리지 않기로 했다. 구현을 시작할 때 사용자가 위치를 정한다. **추천은 기존 `Backend` 안에 트렌드 기능을 추가하는 것**이다. 설정 읽기, Potens·Gemini 모델 배치, 네이버·유튜브 연결 코드를 그대로 다시 쓸 수 있기 때문이다.


## 11. 화면(new.html)에서 바뀌는 점

**핵심 방법:** 더미 데이터를 **API 응답 모양 그대로** 만든다. new.html에는 작은 변환 함수 두 개(`toCardView`, `toReportView`)만 넣어서, 지금 화면 코드가 쓰는 이름으로 바꿔 준다. 나중에 서버가 생기면 "파일 속 더미를 읽는 부분"만 `fetch('/api/trends?tab=...')`로 바꾸면 된다.

| 지금 new.html이 쓰는 이름 | API 스키마 이름 | 변환할 때 |
| --- | --- | --- |
| `id` | `id` | 그대로 |
| `name` | `name` | 그대로 |
| `category` | `category` | 그대로 |
| `aiSummary` | `summary` | 이름만 바꿈 |
| `searchVol` `"58,000"` | `metrics.monthly_search_volume` `58000` | 숫자 → 쉼표 글자 |
| `mentionVol` `"72,000"` | `metrics.monthly_mention_volume` `72000` | 숫자 → 쉼표 글자 |
| `weeklyRate` `"+420%"` | `metrics.weekly_change_rate` `420.0` | 숫자 → `+`/`-`와 `%` 붙인 글자 |
| `platforms` | `platform_share` | 그대로 |
| `status`, `statusType` | `status`, `status_type` | 이름만 바꿈 |
| `whyTrending` `target` `sustainability` | `analysis.why_trending` 등 | 한 단계 안으로 들어감 |
| `relatedKeywords` | `related_keywords` | 이름만 바꿈 |
| `platformTrend.naver` `[..]` | `platform_trend.naver.values` `[..]` | `values`만 꺼냄 |
| (오늘 날짜로 달 이름 계산) | `snapshot.months` | **서버가 준 달을 그대로 씀** |
| 트렌드 강도 HIGH/LOW (변화율 +/-로 추측) | `metrics.trend_strength.label`, `.level` | **서버가 준 글자(강함/보통/약함)를 그대로 쓰고, `level`로 색을 정함** |

**함께 고칠 화면**

- **"급상승 키워드" 탭:** 지금은 옛 "지는 키워드" 모양(📉, 빨간 숫자, 회색 카드)이다. 🔥 아이콘, 초록 숫자, 보통 카드로 바꾼다.
- **리포트 맨 위 딱지:** 탭에 맞게 바꾼다. 트렌드는 "📈 트렌드 리포트 · 지속 성장", 급상승은 "🔥 급상승 리포트 · 급상승"이다.
- **"추천 랭킹순" 정렬:** 지금은 아무 동작이 없다. `rank`를 쓰도록 연결한다.
- **예시 표시:** `is_dummy`가 true면 화면 한쪽에 작게 "예시 데이터" 표시를 둔다.

## 12. 더미 데이터 72개 만드는 규칙 (이 스키마 기준)

- **파일:** `trend_keywords_36.json`(트렌드)과 `surge_keywords_36.json`(급상승). 각 파일은 `{ "snapshot": ..., "tab": ..., "criteria": ..., "items": [KeywordReport × 36] }` 모양이다. 목록 응답은 여기서 리포트 칸을 빼면 된다. 기존 `rising_keywords_36.json`은 지우지 않는다.
- **new.html에도 같은 내용을 넣는다:** 파일을 브라우저로 직접 열면 JSON을 읽어올 수 없기 때문이다.
- **id:** 72개 전체에서 겹치지 않게 `kw_0001` ~ `kw_0072`로 붙인다.
- **기준일:** `2026-09-15`, 달은 `2026-04` ~ `2026-09`.
- **분야 배분:** 탭마다 6개 분야 × 6개씩.
- **5절 규칙을 숫자로 만족시킨다:** 급상승은 전주 대비 +150% 이상, 트렌드는 +150% 미만이면서 규모 기준 이상이고 6개월 +20% 이상이어야 한다.
- **트렌드 강도:** 전주 대비 변화율로 4절 "트렌드 강도 규칙"대로 계산해 넣는다. 더미에서는 작은 숫자 착시 규칙에 걸리는 키워드(지난주 규모가 아주 작은 것)를 만들지 않는다.
- **최신성:** 2026년 여름~9월에 실제로 화제가 된 흐름을 검색으로 확인하고 고른다. 2024~2025년에 반짝하고 끝난 유행은 넣지 않는다.
- **검사 스크립트로 확인할 것:**
  - 플랫폼 비중 합 100
  - 그래프 마지막 값 = 카드 숫자
  - 탭 규칙 만족
  - id 겹침 없음
  - 분야 6×6
  - 빈 글 없음
  - 연관어 5개

## 부록: 현재 저장소 상태와의 차이 (박민규-v1 확인, 2026-09-15)

이 문서가 가정하는 "기존 Backend"는 `박민규-v1` 브랜치에는 없다. `박민규-v1`의 `Final/Backend`는 `origin/Final`의 빈 스켈레톤 그대로다(`app/agents/*.py` 전부 `raise NotImplementedError`, `app/prompts/*.py` 전부 TODO 스텁). 문서가 말하는 "기존에 연결된 네이버 블로그·카페 검색", `FREE_SOURCE_SETUP.md`, `LLM_ROUTE_*` 설정은 전부 `박민규`/`v0-pre-pivot` 브랜치에만 존재한다. 재사용하려면 해당 브랜치에서 필요한 조각(예: `search_tool.py`의 HTTP 클라이언트 부분, `config/settings.py`)만 골라 옮겨야 하며, "기존 Backend를 그대로 쓴다"는 전제는 성립하지 않는다.
