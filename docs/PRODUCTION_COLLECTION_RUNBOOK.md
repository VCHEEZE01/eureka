# 실제 타겟 수집 — 2026-09-14

현재 사용자 화면은 `Final/Frontend/reference-pages/`에서 빌드한 `http://localhost:8000`이다. React 개발 서버는 사용자 테스트 경로가 아니다.

## 변경 원칙

- 기존 120개 주제를 검색 후보로 유지하고 직업별 업무·장소별 행동을 추가한다.
- 검색용 자연어 8개 의도와 판별용 활용형 사전을 분리한다. 불편 표현을 붙이지 않는 상황 탐색도 섞는다. 비용 관련 검색은 지불 의향 판정과 별개다.
- 검색어에 모든 타겟 필드를 강제로 넣지 않는다. 나이·성별·직업·장소는 같은 경험자의 원문 근거로 확인한다.
- 불편 키워드가 없더라도 의미 판별에 포함한다. 실제 불편, 불편 없음, 근거 부족을 구분한다.
- 실제 불편이 있어도 타겟을 확인하지 못하면 검토 후보로 남긴다. 확인되지 않은 자료를 해당 타겟 문제의 근거로 사용하지 않는다.
- 동일 지식iN 질문의 여러 답변을 중복 사례로 세지 않는다. 질문과 답변이 섞여 경험자를 확인할 수 없으면 보류한다.
- 한 번의 탐색 안에서 검색·판별을 이어 처리하고 진행 중 불편 목록도 보여준다. 다음 범위는 명시적인 이어서 탐색 요청으로 진행한다.
- 같은 타겟과 계획 버전의 탐색 이력만 누적한다. 이전 실행 기록은 보존하고 다른 타겟·이전 정책 자료를 섞지 않는다.
- 기존 묶기 관측창은 최근 4주 수집 자료, 근거 상세 조회창은 최근 8주다. 장기 보존 원문 전체를 무기한 재생성 대상으로 삼는 기능은 포함하지 않는다.

## 검색 표현

| 의도 | 예시 |
|---|---|
| 직접 불만 | 불편하다, 번거로워, 답답하다, 귀찮다 |
| 반복·수작업 | 수작업, 일일이 입력, 매번 복사, 중복 입력 |
| 시간·대기 | 오래 걸려, 기다려야, 시간 낭비, 처리 지연 |
| 실패·오류 | 안 돼요, 자꾸 오류, 누락돼, 연동 안 됨 |
| 비용·손실 | 추가 비용, 이중 결제, 환불 안 돼, 수수료 부담 |
| 복잡함·혼란 | 어디서 확인, 찾기 어려워, 절차 복잡, 뭐부터 해야 |
| 기능·정보 부족 | 기능이 없어서, 한 번에 보고 싶다, 알림이 있었으면, 비교하기 어려워 |
| 대안·임시방편 | 방법 없나요, 다른 방법, 결국 엑셀로, 따로 기록 |

사전 정본: `Final/Backend/app/config/dictionaries.py`. 검색 계획 정본: `app/tools/target_query_tool.py`.

## 실행과 사용자 확인

```sh
# Final/Frontend에서
npm run build:single

# Final/Backend에서 — .env의 실제 API 설정 사용
.venv/bin/uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

1. `http://localhost:8000`에서 온보딩 조건을 입력하고 탐색한다.
2. 검색어 목록과 실제 처리 수를 확인한다. 검색 성공에 결과가 없을 수 있으며 API 실패와 구분한다.
3. 발견한 불편과 타겟 확인 문제정의를 따로 본다. 진행 중에도 결과를 열 수 있고, 타겟 미확인·충돌 불편 전체를 20건씩 볼 수 있다.
4. 이전 계획은 “넓어진 범위로 다시 탐색”을 눌러 새 범위를 적용한다. 같은 계획의 미탐색 범위는 이어서 탐색한다. 새로고침은 GET으로 상태를 복원하며 수집을 자동으로 시작하지 않는다.
5. 다른 타겟은 새 탐색으로 시작한다. 같은 타겟의 이전 실행을 이어가는 경우에만 근거를 누적한다.

실제 서비스는 `LLM_DRY_RUN=false`와 실제 모델을 요구한다. 설정·API 호출 실패 시 오류를 표시하고 샘플 응답으로 대체하지 않는다.

## API

`POST /collections`: `{ "target": { "jobs": ["마케터"], "places": ["회사"] } }`.

`POST /collections`: 같은 `target`과 `resume_from`에 이전 실행 ID를 전달해 다음 범위를 수집한다.

`GET /collections/{id}`: 실제 단계, 회차, 검색 계획 범위, 검색어별 결과, 판별·타겟 확인·보류 집계, 검토용 문제를 반환한다.

검색 계획은 `catalog-v4`이며 GET 응답의 `current_plan_version`·`can_resume`로 이전 계획의 재시작을 안내한다. 생성 JSON 필드·타입 오류에는 원래 근거로 한 번 재생성하고 검증한다. `generation_failed`·`generation_retries`를 따로 집계한다.

새 판별 정책은 `evidence_v2`다. 이전 `input_mentions_v1`/미검증 결과는 새 정책 결과로 취급하지 않는다.

기본 탐색 상한은 검색 120회, 요청당 결과 최대 20건, 전체 수집 최대 2,400건, 분야별 판별 최대 1,000건·전체 최대 2,400건, 문제 후보 생성 최대 20개, 모델 논리 호출 최대 200회, 총 3,600초다. 실제 검색 결과 수를 보장하지 않는다. 환경 설정으로 조절하며 모델 timeout·batch·재시도 설정도 상속한다. 요청당 결과 설정은 최대 100까지 가능하나 각 검색 제공자의 페이지 한도를 따른다.

## 남는 한계

- 현재 검색 API가 제공하는 제목·요약을 사용한다. 원문 전체를 읽었다고 표시하지 않는다. 잘린 문장이나 불명확한 경험자는 보류한다.
- 금융·건강은 기존 뉴스 출처 제한을 유지한다. 개인 경험 출처 확대와 출처 독립성의 정의는 별도 운영 과제다. 뉴스의 배경 정보만으로 개인의 불편을 만들지 않는다.
- 나이·성별 등을 직접 밝히지 않은 글이 많으므로, 조건이 많을수록 확인된 타겟 근거가 적을 수 있다. 미확인 속성을 추정해 수를 채우지 않는다.
- 검색 결과 수는 모집단의 불편 빈도가 아니다. 회차별 예산과 게시 품질 기준은 구분한다.
- 검토용 초안은 자동 공개하지 않는다. 기존 사례·출처·근거 기준과 내용 검수를 유지한다.

## 검증 기록

- 백엔드 전체 615개 통과(기존 의존성 폐기 예정 경고 2개), 프론트 34개 통과, 단일 HTML 빌드 완료.
- 첫 120개 검색의 기본 120주제 포함, 첫 40개 검색의 9개 의도(8불편+상황), 카탈로그 중복 제거를 검증했다. 2,400건 수집·전량 판별·전체 검토 목록 반환을 모의 통합 테스트로 확인했다.
- 네이버 뉴스·지식iN·카페 및 다음 블로그 검색 endpoint 실호출 4건이 정상 응답했다. 세 요청은 0건, 다음 블로그 요청은 5건으로 정상 빈 결과와 성공 응답을 구분했다. 기록: `Final/Backend/data/quality-eval/search-endpoints-real.json`.
- 브라우저에서 이전 실행 차단과 온보딩 복귀를 확인했다. 실제 서비스 설정 `LLM_DRY_RUN=false`를 저장했다.
- 기존 게시글 38건을 Gemini에 보내는 검증은 자동 승인 검토에서 구체적인 데이터 전송 승인 부족으로 거절되어 실행하지 않았다. 이번 확대 범위의 실제 API 전체 실행은 하지 않았다. 위 자동 테스트는 모델 정확도의 실데이터 평가 결과가 아니다.

사용자가 직접 실행한 이전 계획의 실제 기록(`col-9bc8300dfe264848b2c192eb`): 중복 제거 후 278건 수집 → 200건 판별 → 불편 14건 → 타겟 확인 불편 2건 → 문제정의 1개. 후보 하나는 JSON 필드 계약 오류로 생성 실패했다. 기록은 보존하며 확대 이후 성과로 표시하지 않는다.
