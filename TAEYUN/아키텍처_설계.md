## 1. 기술 스택

| 영역 | 선택 | 이유 |
| :-- | :-- | :-- |
| Backend | **Python + FastAPI** | 묶기(임베딩·클러스터링)가 파이썬 생태계에 있음 · 팀 경험 있음 |
| Agent workflow | **LangGraph** | F00이 순서+분기 구조(보류/병합/반려)라 실제로 값을 함 |
| Frontend | **React + TypeScript + Vite** | 백엔드 분리 후 Next.js 서버 기능이 불필요해짐 · 단일 HTML 빌드가 간단해짐 |
| Database | **미정** ⚠️ | 2절 결정사항 참조 |
| LLM | **미정** ⚠️ | 에이전트 구현 단계에서 확정 |
| Auth | 이메일 기반 가정 *(PRD TBD)* | |

### 프론트엔드 이전에 대해

기존 Next.js 프로토타입에서 **화면 코드는 거의 그대로 옮겨진다.**
라우팅을 `lib/nav.tsx`로 추상화해뒀기 때문에, 화면은 `next/navigation`을 직접 부르지 않는다.
바뀌는 것은 **라우팅 껍데기뿐**이고 `screens/` `components/` `data/`는 그대로다.

## 3. 전체 기능 흐름

유레카는 성격이 다른 **두 개의 흐름**을 가진다. 이것이 구조의 핵심이다.

```
┌─ [배치] 미리 돌려두는 흐름 (F00) ─────────────────────┐
│                                                       │
│  스케줄러 → 검색어 생성 → 소스별 수집 → 불편 판별      │
│           → 임베딩 → 묶기 → 문제정의 작성 → 검수       │
│           → 게시 / 보류 / 병합                         │
│                                                       │
│  · 사용자 요청과 무관하게 돈다                          │
│  · 분~시간 단위                                        │
│  · 실패해도 사용자에게 보이지 않는다                     │
└───────────────────────────────────────────────────────┘
                          ↓ 문제 풀을 채움
┌─ [실시간] 사용자가 누를 때 도는 흐름 ──────────────────┐
│                                                       │
│  읽기 (F03·F04·F06)      → 밀리초, 캐시된 것 그대로     │
│  합성 (F02캐시미스·F05·F07) → 수 초, 진행 상태 스트리밍  │
│                                                       │
└───────────────────────────────────────────────────────┘
```

**PRD F00의 하이브리드 방침이 이 그림이다.**

## 4. Backend / Frontend 역할 분리

| | Backend (FastAPI) | Frontend (Vite) |
| :-- | :-- | :-- |
| 책임 | 데이터·판단·집계 | 표시·입력·상태 |
| 갖는 것 | DB · 에이전트 · 외부 API 키 | 화면 · 디자인 토큰 |
| **절대 안 하는 것** | 화면 렌더링 | **숫자 계산 · LLM 직접 호출 · API 키 보관** |

### 핵심 원칙 — 숫자는 Backend 집계에서만

PRD 8절 "근거 없는 수치 생성 금지"를 **구조로 강제한다.**

- `caseCount`, `sourceCount` 같은 숫자는 **DB를 세서** 만든다
- **LLM 출력 스키마에 숫자 필드를 아예 두지 않는다** → 지어낼 수 없음
- Frontend는 받은 숫자를 표시만 한다

문서에 "하지 말자"라고 쓰는 대신, 스키마 레벨에서 불가능하게 만드는 방식이다.

## 5. AI Agent 역할 분리

### 5-1. 배치 그래프 — 수집 (F00)

| 노드 | 역할 | LLM |
| :-- | :-- | :-- |
| `plan_queries` | 카테고리·소스 → 검색어 목록 생성 | ○ |
| `collect` | 소스별 검색 실행 (병렬) | ✕ tool |
| `judge` | 각 글이 "진짜 불편"인지 판별 | ○ |
| `embed` | 벡터 생성 | ✕ tool |
| `cluster` | 비슷한 것끼리 묶기 | ✕ tool |
| `draft` | 묶음 → 제목·설명·맥락 작성 | ○ |
| `review` | 근거 충분한가 · 기존과 중복인가 | ○ + DB |
| `publish` | 게시 / 보류 / 병합 | ✕ |

```
plan_queries → collect → judge → embed → cluster → draft → review
                                                              │
                                          ┌───────────────────┼───────────────┐
                                          ▼                   ▼               ▼
                                       publish              hold           merge
                                      (게시)             (근거 부족)      (중복 병합)
```

**이 분기가 LangGraph를 쓰는 이유다.** 단순 순차 실행이 아니다.

### 5-2. 실시간 그래프

| 그래프 | 노드 | PRD |
| :-- | :-- | :-- |
| **조합** | `load_problems` → `find_common` → `draft_combined` → `summarize_evidence` | F05 |
| **개인화** | `load_base` → `load_pool` → `adapt` → `explain_fit` → `scope_by_resource` | F07 |
| **아이디어** | `diversify` → `detail` | F06 |

각 노드가 끝날 때마다 진행 상태를 프론트로 흘려보낸다 → **에이전틱 진행 상태 UI**.

## 6. Tool / API 호출 구조

### 원칙 — Agent는 외부를 직접 호출하지 않는다

```
Agent  →  Tool  →  외부 API / DB
  ✕ Agent ──────→ 외부 API   (금지)
```

이유: 테스트할 때 Tool만 가짜로 바꾸면 되고, API 키가 한 곳에만 모인다.

| Tool | 하는 일 |
| :-- | :-- |
| `naver_search_tool` | 네이버 검색 API |
| `kakao_search_tool` | 카카오 검색 API |
| `public_data_tool` | 공공데이터 (민원·소비자상담) |
| `embedding_tool` | 텍스트 → 벡터 |
| `cluster_tool` | 벡터 묶기 (순수 계산, LLM 없음) |
| `db_tool` | 저장·조회 |
| `dedupe_tool` | 기존 문제와 유사도 비교 |

## 7. Prompt 관리 구조

프롬프트는 **코드에 섞지 않고** `prompts/`에 분리한다.

```
prompts/
├─ common_prompts.py      공통 규칙 (PRD 8절 AI 정책을 여기 한 번만)
├─ collect_prompts.py     검색어 생성 · 불편 판별
├─ problem_prompts.py     문제정의 작성 · 검수
├─ idea_prompts.py        아이디어 생성
└─ personalize_prompts.py 조합 · 개인화
```

`common_prompts.py`에 들어갈 것 — 모든 프롬프트가 상속받는 금지 사항:

- 근거 없는 수치(시장 규모·성공 확률·사례 수)를 만들지 않는다
- 아이디어는 "추천 후보"로만 표현한다
- 원문을 통째로 복제하지 않는다

## 8. Schema / 데이터 모델

### 8-1. DB 테이블

| 테이블 | 내용 | 근거 |
| :-- | :-- | :-- |
| `sources` | 출처 매체 | F04 출처 분포 |
| **`raw_items`** | **수집 원문 1건** | **모든 숫자·근거의 원천** |
| `problems` | 문제정의 | F03·F04 |
| `evidences` | 문제 ↔ 원문 연결 + 요약 | F04 |
| `ideas` | 기본 아이디어 | F06 |
| `users` | 계정 | F10 |
| `scopes` | 사용자가 고른 수집 범위 | F02 |
| `scope_cache` | 범위 조합 → 문제 목록 | F00 캐시 |
| `combined_problems` | 조합된 문제정의 | F05 |
| `personalize_runs` / `personalized_ideas` | 개인화 실행·결과 | F07 |
| `saves` | 즐겨찾기 | F09 |

### 8-2. 지켜야 할 3가지

1. **숫자는 저장하지 말고 센다** — `caseCount`는 `raw_items` 집계
2. **모든 근거는 원문으로 역추적된다** — `evidence → raw_item → source`
3. **AI가 쓴 문장은 필드가 분리된다** — 화면에서 근거/AI를 구분해야 하므로

### 8-3. 계약

```
pydantic (Backend)  ──API 응답──▶  TypeScript types (Frontend)
```

**API 계약을 먼저 고정하고** 양쪽이 거기에 맞춘다. 스키마가 바뀌면 양쪽 다 바꾼다.

## 11. 개발 단계 순서

**ㄴ(화면·에이전트 완성) → ㄱ(실제 수집)** 순서.
각 단계가 끝날 때마다 **돌아가는 상태**를 유지한다.

| Phase | 내용 | 끝나면 |
| :-- | :-- | :-- |
| **0** | 폴더 생성 · **Schema 정의** · **API 계약 고정** · DB 연결 · 더미 시딩 | 계약이 고정됨 |

## 12. 테스트 전략

| 대상 | 방법 | 왜 |
| :-- | :-- | :-- |
| **Tool** | 외부 API를 가짜로 바꿔 테스트 | 실제 API 호출 없이 · 무료 · 빠름 |
| **Agent** | 고정 입력 → 출력 스키마 검증 | LLM 출력이 흔들려도 **모양은** 지켜지는지 |
| **Workflow** | 분기별 경로 검증 (게시/보류/병합) | F00 분기가 의도대로 도는지 |
| **API** | 요청 → 응답 스키마 검증 | 프론트와의 계약 |
| **금지 사항** | 출력에 숫자 필드가 없는지 자동 검사 | PRD 8절을 테스트로 강제 |

마지막 항목이 중요하다. **"근거 없는 수치 생성 금지"를 사람이 지키는 게 아니라 테스트가 막는다.**
