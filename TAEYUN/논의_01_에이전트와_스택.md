## 0. 이 논의의 순서

스택을 먼저 고르면 대개 후회한다. 그 앞에 답해야 할 질문이 있다.

> **에이전트가 이 서비스에서 정확히 뭘 하는가?**

이게 정해지면 스택은 거의 자동으로 따라온다.

## 1. 유레카의 에이전트는 뭘 하나

PRD F00·F05·F06·F07에서 뽑아낸 후보 역할이다. **아직 확정 아님.**

### A. 수집 쪽 (F00) — 미리 돌려두는 것

| 역할 | 하는 일 |
| :-- | :-- |
| 수집 | 소스별로 검색어 만들어서 원문 긁어오기 |
| 해석 | 긁어온 글이 "진짜 불편"인지 판별 · 요약 |
| 묶기 | 비슷한 불편끼리 뭉쳐서 문제정의 후보 만들기 |
| 작성 | 제목 · 설명 · 맥락 쓰기 |
| 검수 | 근거 부족하면 보류, 중복이면 병합·반려 |

### B. 실시간 쪽 — 사용자가 누를 때 도는 것

| 역할 | 하는 일 | PRD |
| :-- | :-- | :-- |
| 조합 | 문제 2~3개를 하나의 문제정의로 합치기 | F05 |
| 개인화 | 조건에 맞춰 아이디어 좁히기 | F07 |
| 아이디어 | 문제에서 해결 방향 뽑기 | F06 |

**에이전트를 붙일 자리는 충분하다.**
특히 A는 순서가 있고 분기가 있어서(근거 부족 → 보류, 중복 → 병합)
LangGraph 같은 워크플로우 도구가 실제로 값을 한다. 억지로 끼워넣는 게 아니다.

## 2. 워케이션 프로젝트와 결정적으로 다른 축

워케이션은 (확인 필요) **"사용자 요청 하나 → 여러 에이전트가 붙어서 → 결과"** 형태였을 것으로 추정.

유레카는 거기에 **축이 하나 더 있다.**

```
[배치]   미리 돌려서 문제 풀을 채워둠       ← 무겁고, 느리고, 사용자와 무관
   ↓
[실시간] 사용자가 누르면 그 자리에서 합성    ← 워케이션과 비슷한 구조
```

그리고 **제품의 핵심 가치가 위쪽(배치)에 있다.**
"근거 데이터 기반"이 유레카의 차별점인데, 그게 배치로 쌓는 부분이다.
실시간은 그 위에 얹히는 것이다.

### 이 축이 생기면 달라지는 것

- 배치는 웹 서버와 완전히 분리해야 한다
- 스케줄러가 필요하다
- 배치가 실패해도 사용자에게 보이면 안 된다

**→ 확인 필요: 워케이션에 배치로 미리 데이터를 쌓아두는 부분이 있었는가?**
없었다면 이번에 새로 생기는 축이므로 미리 알아야 한다.

## 3. 스택을 가르는 핵심 질문

판단 기준은 몇 개 안 된다. 그중 결정적인 건 하나다.

> **"비슷한 불편끼리 묶는" 작업을 어떻게 할 것인가**

이게 파이썬이 확실히 유리한 거의 유일한 지점이다.
나머지(LLM 호출, API 서버, 크롤링)는 사실 양쪽 다 된다.

### 추가로 얹히는 요인

**태윤님이 이미 FastAPI + LangGraph를 해봤다는 것.**
마감이 있는 프로젝트에서 새 도구를 배우는 건 리스크이므로 무시할 수 없는 요인이다.
