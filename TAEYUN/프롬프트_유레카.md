## 1. 메인 프롬프트 (전체 설계용)

아래 블록을 통째로 복사해서 쓰세요.

```text
나는 "유레카(Eureka)"라는 AI 에이전트 기반 웹앱을 만들려고 한다.

■ 서비스 목적
실제 사용자가 남긴 불편 데이터에서 문제를 발굴하고, 그 근거와 함께
실행 가능한 서비스 아이디어로 연결한다.
"만들 능력은 있지만 무엇을 만들지 모르는" 메이커의 아이템 선정 문제를 해결한다.

■ 대상 사용자
방향성이 없는 초기 메이커.
- AI 코딩 도구로 빠르게 MVP를 만들 수 있으나 아이템 선정에서 막히는 사람
- 사이드 프로젝트를 여러 번 시도했지만 문제 검증 단계에서 멈춘 사람
- 1인 창업자, 프리랜서, 예비 창업자

■ 사용자 입력
1. 리서치 범위: 수집 소스 복수 선택 (커뮤니티 / 블로그 / 리뷰 / 뉴스 / 소셜)
2. 문제 탐색: 검색어, 카테고리(생산성·업무 / 커리어·자기계발 / 라이프스타일), 정렬
3. 문제 조합: 기존 문제 중 2~3개 선택 (임의 텍스트 입력 불가)
4. 개인화 조건: 서비스 형태 / 타깃 / 리소스 / 추가 조건(500자 이내)

■ AI가 해야 할 일
[배치 — 미리 돌려두는 것]
- 소스별 검색어 생성 후 원문 수집
- 수집된 글이 실제 "불편"인지 판별
- 비슷한 불편끼리 묶어 문제 후보 생성
- 문제정의(제목·설명·발생 맥락) 작성
- 검수: 근거가 충분한가 / 기존 문제와 중복인가 → 게시·보류·병합 판단
- 문제별 기본 아이디어 3~5개 생성 (서로 다른 해결 접근으로)

[실시간 — 사용자가 누를 때]
- 문제 2~3개를 하나의 새 문제정의로 합성
- 사용자 조건에 맞춰 아이디어 재구성 + 조건 적합 이유 설명

■ 최종 결과물
- 문제 카드 목록: 제목, 한 줄 요약, 카테고리, 대표 근거, 출처, 관련 사례 수
- 문제 상세: 사용자 불편 요약 3~5건, 출처 분포, 발생 맥락, 비슷한 문제
- 아이디어: 이름, 한 줄 설명, 타깃, 형태, 문제 연결 이유, 해결 방식, 핵심 기능, 차별점
- 개인화 아이디어: 위 항목 + 조건 적합 이유 + 리소스 대비 권장 범위
- 보관함: 저장한 문제·아이디어

■ 필요한 외부 데이터/API
- 네이버 검색 오픈API (블로그·카페·지식iN·뉴스·웹문서), 일 25,000회 무료
- 카카오 다음 검색 API, 무료
- 네이버 데이터랩 (추세 신호, 상대 지수만 제공)
- 공공데이터 (국민권익위 민원, 한국소비자원 상담사례)
- 임베딩 (API 또는 로컬 모델)
- LLM API
※ 최종 소스 목록은 아직 미확정

■ 사용 환경
웹앱 (데스크톱 우선, 모바일 대응).
추가로 서버 없이 더블클릭으로 열리는 단일 HTML 공유본이 계속 필요하다.

■ 기술 스택 선호
- Backend: Python FastAPI
- Frontend: React + TypeScript + Vite
- Agent workflow: LangGraph
- Database: 미정 (SQLite / PostgreSQL+pgvector / Supabase 검토 중)
- Auth: 로그인 필요. 단 비로그인 열람 구간이 있음
  · 비로그인 가능: 랜딩, 문제 탐색, 문제 상세, 기본 아이디어
  · 로그인 필요: 즐겨찾기, 보관함, 문제 조합, 개인화

■ 반드시 지켜야 할 제약 7가지
이 제약들이 이 프로젝트를 일반적인 에이전트 프로젝트와 다르게 만든다.

1. 실행 축이 두 개다.
   배치(문제 풀을 미리 채움)와 실시간(조합·개인화)은 성격이 완전히 다르다.
   배치는 웹 서버와 분리되어야 하고, 실패해도 사용자에게 보이면 안 된다.

2. 근거 없는 수치를 생성하면 안 된다.
   관련 사례 수, 출처 수 같은 숫자는 반드시 DB 집계에서 나와야 한다.
   LLM이 숫자를 지어내지 못하도록 구조적으로 막아야 한다.

3. 실제 수집된 근거와 AI가 생성한 설명을 화면에서 시각적으로 구분해야 한다.
   따라서 데이터 모델에서도 두 영역이 섞이면 안 된다.

4. 단일 검증점수를 제공하지 않는다.
   대신 근거 건수와 출처 수로 신뢰를 표현한다.

5. 같은 입력이면 항상 같은 결과가 나와야 한다.
   사용자가 보관함에서 다시 열었을 때 내용이 바뀌면 안 된다.

6. 실시간 생성이 일어나는 3개 지점에서 진행 상태를 단계별로 보여줘야 한다.
   (리서치 범위 첫 설정 / 문제 조합 / 개인화)
   따라서 API가 단발 응답이 아니라 스트리밍이어야 한다.

7. 서버 없이 도는 단일 HTML 공유본을 계속 유지해야 한다.
   따라서 mock 데이터로만 도는 경로가 항상 살아있어야 한다.

■ 원문 복제 정책
원문 전체를 복제하지 않고 요약을 기본으로 한다.
허용되는 경우에만 짧은 발췌와 원문 링크를 제공한다.

───────────────────────────────────

먼저 코딩하지 말고, 위 정보를 바탕으로 전체 시스템 아키텍처를 설계해줘.

설계에는 반드시 아래 항목을 포함해줘:
1. 전체 기능 흐름
2. Backend / Frontend 역할 분리
3. AI Agent 역할 분리
4. Tool/API 호출 구조
5. Prompt 관리 구조
6. Schema/데이터 모델 구조
7. 화면 구성
8. 폴더 구조
9. 개발 단계 순서
10. 테스트 전략

특히 아래 3가지에 대해 명확한 근거와 함께 답해줘:
- "비슷한 불편끼리 묶는" 작업을 어떤 방식으로 처리할 것인가
- LLM이 숫자를 지어내지 못하게 하는 구조적 장치는 무엇인가
- 배치와 실시간을 어떻게 분리할 것인가
```

## 2. 부분 질문용 프롬프트

전체가 아니라 특정 결정만 물어볼 때 씁니다. 앞에 **1번 프롬프트를 먼저 붙이고** 아래를 이어서 던지세요.

### 2-1. 묶기 방식 (스택을 가르는 핵심)

```text
위 프로젝트에서 "수집한 원문 수백~수천 건을 비슷한 불편끼리 묶어
문제 후보를 만드는" 단계를 어떻게 구현할지 비교해줘.

비교 조건:
- 원문은 한국어이고, 커뮤니티 글·리뷰·질문글이 섞여 있다
- 최종적으로 문제 10~20개를 만들어야 한다
- 같은 입력이면 같은 결과가 나와야 한다
- 나중에 새 원문이 들어오면 기존 문제에 붙일지 새로 만들지 판단해야 한다

각 방식에 대해 알려줘:
1. 구현 난이도와 필요한 라이브러리
2. 처리 가능한 규모
3. 비용
4. 결과의 재현성
5. Python이 아닌 TypeScript로 했을 때 얼마나 불리한가
6. 이 프로젝트에 대한 최종 추천과 그 이유
```

### 2-2. 데이터베이스 선택

```text
위 프로젝트에 적합한 데이터베이스를 추천해줘.

고려사항:
- 임베딩 벡터를 저장하고 유사도 검색을 해야 한다
- 원문(raw item) 수천~수만 건이 쌓인다
- 팀 규모가 작고 인프라 운영 경험이 적다
- 파이널 프로젝트이므로 설정 비용이 낮을수록 좋다
- 나중에 확장 가능성도 남겨두고 싶다

SQLite / PostgreSQL+pgvector / Supabase 를 비교하고,
각각의 경우 임베딩 검색을 어떻게 처리하게 되는지 구체적으로 알려줘.
```

### 2-3. 검수 자동화 여부

```text
위 프로젝트의 배치 파이프라인에는 이런 판단 단계가 있다.

"근거가 부족하면 게시 보류 / 기존 문제와 중복이면 병합 또는 반려"

이 판단을 전부 AI에게 맡길 것인지, 사람이 확인하는 관리자 화면을 둘 것인지
장단점을 비교해줘.

특히 알려줘:
- 전자동으로 갈 때 생길 수 있는 실패 유형
- 사람 검수를 넣으면 추가로 필요한 화면과 작업량
- 파이널 프로젝트 규모에서 현실적인 선택
- 중간 형태(예: 자동 처리하되 이상한 것만 사람에게)가 가능한지
```

### 2-4. 진행 상태 스트리밍

```text
위 프로젝트는 실시간 생성이 일어나는 3개 지점에서
에이전트의 진행 단계를 사용자에게 보여줘야 한다.

FastAPI + LangGraph 환경에서 이걸 구현하는 방법을 비교해줘.
- SSE / WebSocket / 폴링 각각의 장단점
- LangGraph의 노드 실행을 어떻게 프론트로 흘려보내는가
- 중간에 실패했을 때 처리
- React 쪽에서 받는 코드 구조
```

## 3. 구현 지시 프롬프트 (설계 승인 후 사용)

```text
이제 위 설계를 바탕으로 실제 프로젝트를 구현해줘.

개발 원칙:
- 먼저 전체 폴더 구조를 만든다
- 데이터 schema를 먼저 정의한다
- Backend API 계약을 먼저 고정한다
- AI Agent는 역할별로 분리한다
- Agent가 직접 외부 API를 호출하지 않고 tools를 통해 호출하게 한다
- Prompt는 prompts 폴더에 분리한다
- Workflow는 graph 폴더에서 관리한다
- Frontend는 API 응답 타입에 맞춰 구현한다
- mock 데이터로 UI를 먼저 검증한 뒤 실제 API와 연결한다
- 각 단계마다 실행 가능한 상태를 유지한다
- LLM 출력 스키마에는 숫자 필드를 두지 않는다 (숫자는 DB 집계에서만)
- 단일 HTML 공유본이 계속 빌드되는지 각 단계마다 확인한다

진행 순서:
1. 프로젝트 초기 구조 생성
2. Backend 기본 서버 구성
3. Schema 정의
4. Tool 함수 구현
5. Prompt 작성
6. Agent 구현
7. Workflow 연결
8. API route 연결
9. Backend 테스트 작성
10. Frontend 초기 구성
11. 화면별 컴포넌트 구현
12. API client 구현
13. mock 데이터 연결
14. 실제 Backend API 연결
15. 실행 방법과 README 작성

완료 후:
- 전체 폴더 구조
- 실행 방법
- 주요 파일 역할
- 테스트 방법
- 앞으로 확장할 수 있는 지점
을 정리해서 알려줘.
```

## 5. 다른 AI 답변을 받았을 때 확인할 것

돌려받은 설계안이 아래를 만족하는지 보면 됩니다.
**대부분의 AI가 이 7개 제약을 빠뜨립니다.**

- [ ] 배치와 실시간을 분리했는가 (하나로 합쳐놨으면 유레카를 이해 못 한 것)
- [ ] 숫자를 LLM이 못 만들게 하는 장치가 있는가
- [ ] 근거와 AI 설명이 데이터 모델에서 분리되어 있는가
- [ ] 검증점수를 만들어내지 않았는가
- [ ] 같은 입력 → 같은 결과가 보장되는가
- [ ] 진행 상태 스트리밍이 API 설계에 반영됐는가
- [ ] mock 전용 경로가 살아있는가 (단일 HTML 공유본용)
